# Ouroboros Development Guide

## Repository Layout

- `cmd/ouro/`: Cobra CLI entrypoint for `init`, `doctor`, `run`, `replay`, and toolchain commands.
- `internal/app/`: workspace initialization, doctor validation, provider config, and production run orchestration.
- `internal/domain/`: Domain Pack SDK plus Web/API, Infra/Internal, and CTF/Lab packs.
- `internal/toolchain/`: native toolchain manifest loading, appsec tool catalog metadata, authored native tool validation, health checks, and corpus helpers.
- `internal/compiler/`: semantic action to toolchain plan compilation and parser binding.
- `internal/eventlog/`: SQLite event log and replay snapshot projection.
- `internal/evidence/`, `internal/blackboard/`, `internal/frontier/`: core state, graph, coverage, and breadth/depth primitives.
- `internal/swarm/`, `internal/modelruntime/`, `internal/patterns/`: agent contracts, timeline lanes, model runtime telemetry, and strategy patterns.
- `internal/tui/`: Bubble Tea TUI shell, panels, graph stack, runtime tabs, and replay projection.
- `internal/report/`: Evidence Graph to report projection and Markdown rendering.
- `toolchains/`: bundled toolchain manifests with optional managed dependency metadata for appsec and artifact-analysis tools.
- `configs/patterns/`: built-in strategy pattern YAML files.
- `docs/progress/`: milestone progress records. Add or update one before marking a milestone complete.
- `model/`: immutable upstream reference archives. Do not modify these files.
- `.analysis/`: regenerated scratch extraction workspace for reference-code review only.

`make release` writes a local tarball and `SHA256SUMS` under `dist/`. The release script respects `VERSION`, `DIST_DIR`, `GOOS`, `GOARCH`, and `GOPROXY`; it builds one target tuple and does not publish artifacts.

`scripts/install.sh` installs only from a local release archive or extracted release directory. It deliberately rejects HTTP(S) sources, writes to `${PREFIX:-$HOME/.local}/bin/ouro`, and requires no network access.

`make doctor` creates a temporary workspace, initializes it, and runs `ouro doctor` against it. `make doctor-strict` runs the same initialized workspace through `ouro doctor --require-safety-authorization`, which is the CI-oriented safety-bypass gate.

## Run Event Streaming

`internal/app.RunWorkspaceWithOptions` accepts `RunOptions` with event and snapshot observers. Observers are called only after the event has been appended to SQLite, so they receive durable event IDs and timestamps. Snapshot observers receive replay snapshots rebuilt from the persisted events seen so far.

Use this path when wiring live TUI updates or external telemetry. Keep `RunWorkspace` as the no-observer convenience wrapper. `ouro run --interactive` uses this path and sends each snapshot to the active TUI session as `tui.ReplaySnapshotMsg`.

Runtime stage markers are stored as `eventlog.EventAttempt` payloads with `kind: stage`, `stage_id`, and `status`. Keep stage events deterministic and ordered so replay and live TUI can explain where execution is.

Current staged run boundaries are `workspace-bootstrap`, `toolchain-health`, `hypothesis-seeding`, `tool-execution`, and `report-projection`. The default run path emits the report-ready replay event inside the report-projection stage, and the final durable event for a successful deterministic run is `report-projection:completed`. `RunOptions.DeferReportProjection` / `ouro run <workspace> --defer-report-projection` is the explicit close/off path for synchronous report generation: it records `report-projection:skipped` with reason `deferred`, returns `report: not-generated`, and writes no Markdown or `report_ready` event. `ProjectRunReport` / `ouro report-project <workspace> <run-id> --write` can later replay that run, render the Markdown report under `workspace/reports/<run-id>.md`, append `report_ready`, and close the report-projection stage with `completed`; without `--write` it is a metadata-only dry-run preview that prints the target path as `planned_report`. `report_ready` is appended only after the Markdown write succeeds, so failed report writes leave replay at `report: not-generated`. This report path reads replay/evidence only and does not run workspace doctor/container-runtime checks, run tools, dispatch workers, contact endpoints or targets, submit results, acknowledge requests, mutate leases, or apply daemon controls.

`CreateReportProjectionDispatch` / `ouro report-project-dispatch <workspace> <run-id>` persists a dry-run metadata-only review artifact under `workspace/reports/report-projection-dispatches/`, including replay event count and replay digest. `ouro report-project-dispatches <workspace> [artifact]` lists or inspects those artifacts with the target Markdown path labeled as `planned_report`. Dispatch artifacts are review input only: they do not write Markdown, append `report_ready`, start or complete the report-projection stage, run doctor/container-runtime checks, execute tools, dispatch workers, contact endpoints or targets, submit results, acknowledge requests, mutate leases, or apply daemon controls. `ExecuteReportProjectionDispatch` / `ouro execute-report-project-dispatch <workspace> <artifact> --execute` is the separate default-off execution gate: it requires the explicit flag before reads that can lead to writes, re-reads a workspace-confined dry-run dispatch artifact, rejects symlinked dispatch files/directories and nested artifact paths, revalidates version/status/mode, computed report path, replay event count, and replay digest, and passes the same expected count/digest into the safe report projection writer before the first projection event append. It appends `report_ready` only after Markdown write success and writes an execution audit under `workspace/reports/report-projection-dispatch-executions/`; failed writes refresh replay/report state before writing the failed audit. Stale dispatches, same-count replay mutations, and already projected runs fail before Markdown or execution-audit writes. `ListReportProjectionDispatchExecutions`, `ReadReportProjectionDispatchExecution`, and `ouro report-project-dispatch-executions <workspace> [artifact]` expose those audits.

`AnnotateReportProjectionDispatchExecution` / `ouro report-project-dispatch-execution-annotate <workspace> <execution>` rewrites only that workspace-confined execution audit with an explicit `accepted`, `deferred`, or `rejected` decision; `false-positive` is rejected so authorized false-positive review state is recorded as `rejected` plus `reason` metadata. `SelectReportProjectionDispatchExecution` / `ouro report-project-dispatch-execution-select <workspace> <execution>` writes the current report marker at `workspace/reports/report-projection-selection.json` only after the referenced execution is version 1, completed, execute-mode, written, report-path-safe, and annotated `accepted`. `ReadReportProjectionDispatchExecutionSelection` / `report-project-dispatch-execution-selection` inspects the marker, and `ClearReportProjectionDispatchExecutionSelection` / `report-project-dispatch-execution-selection-clear` rewrites that same marker to `status=cleared` so current-report focus has a close/off path. Missing, deferred, rejected, stale, tampered, outside-path, or symlinked inputs fail before marker writes. Workspace-bound TUI Timeline Lanes lists dispatch/execution artifacts, annotation rows, review rows, current/cleared selection rows, and supports double-confirm `x` on dry-run metadata-only dispatch artifacts through the same `ExecuteReportProjectionDispatch` gate as `execute-report-project-dispatch --execute`; the first press only arms confirmation, the second writes Markdown plus one execution audit through the app gate and selects the new execution audit row. Non-dry-run dispatch artifacts remain read-only. Timeline Lanes also supports double-confirm `x` for metadata-only current select/clear. Hosted replay workbench startup loads report execution audits and the current/cleared report marker, then exposes them through `GET /api/reports`, `GET /api/report-selection`, `window.OURO_REPLAY_REPORTS`, `window.OURO_REPLAY_REPORT_SELECTION`, and local HTML summaries. Browser `POST /api/reports` always remains rejected; browser `POST /api/report-selection` remains rejected by default and is enabled only by `replay-workbench --enable-report-selection-writes`, where it accepts structured `select` / `clear` JSON and rewrites only the same closeable report marker. TUI dispatch execution does not execute tools, dispatch workers, contact endpoints or targets, submit results, acknowledge requests, mutate leases, or apply daemon controls. Annotation, selection, and hosted report review paths do not write Markdown, append `report_ready`, mutate replay events, execute tools, dispatch workers, contact endpoints or targets, submit results, acknowledge requests, mutate leases, or apply daemon controls. `report-project --write` remains the direct explicit report writer.

`RunWorkspaceWithOptions` also accepts a `ToolRunner`. Use this to replace the default offline runner with a sandboxed worker implementation. `RunOptions.Action` and `ouro run --action <semantic_action>` select the compiler action for a run; the empty/default action remains `discover_assets`, while explicit `fingerprint_surface` can surface app/artifact analysis tool-level nodes. Unknown action values fail at compile time instead of silently falling back. Tool execution events should use `execution_id`, `execution_status`, `action`, `capability`, `runner`, and `parser` fields rather than overloading tool health fields.

Replay projection maps `execution_status: failed` to runtime toolchain status `failed`, so live TUI snapshots and `ouro replay` surface failed worker runs. Report paths are derived only from `report_ready` replay events; failed runs without report projection display `report: not-generated`.

`ouro replay <workspace> <run-id> --format text|json|ndjson` controls replay export format. `text` is the default human summary and remains compatible with `--tui` and `--interactive`. `json` writes one structured document with run id, event count, lane counts, status, report path, and timeline events including raw payloads. `ndjson` writes one JSON timeline event per line for external tooling. Non-text exports are read-only and cannot be combined with `--tui` or `--interactive`, so export mode never launches the TUI or starts a run.

Runtime worker registration metadata is stored under `workspace/runtime/workers/<worker-id>.json`. `ouro runtime worker-register <workspace> <worker-id>` writes or updates a metadata-only registration with mode, status, endpoint, capabilities, labels, `registered_at`, and `heartbeat_at`. `ouro runtime worker-heartbeat <workspace> <worker> [--status <status>]` updates the same workspace-confined artifact from an external process, refreshing `heartbeat_at` and optionally moving status among `available`, `busy`, `draining`, and `offline`. `ouro runtime workers <workspace>` lists registered workers, and `ouro runtime workers <workspace> <worker>` inspects one by id, basename, or workspace-confined path. Workspace-bound TUI models render registered workers in Agent Runtime and mark non-offline workers as `stale` when their heartbeat is older than the local stale threshold. This registry is visibility and placement groundwork only; it does not create a remote process, acquire queue claims, or dispatch remote work yet.

Runtime worker placement planning is also metadata-only. `PlanRuntimeWorkerPlacements` compiles the workspace `discover_assets` tool plan, reads registered runtime workers, applies worker freshness/capability checks plus pack-policy skips, and returns ready/skipped placement candidates with worker id, endpoint, planned local pool id, execution id, capability, and carried `tool_plan` metadata. `CreateRuntimeWorkerPlacementPlan` and `ouro runtime worker-placement-plan <workspace> [--run-id <run>]` persist that dry-run plan under `workspace/runtime/worker-placement-plans/*.json`; `ouro runtime worker-placement-plans <workspace> [plan]` lists or inspects those artifacts. Planning does not create queue claims, does not mark workers busy, does not acknowledge outbox requests, does not contact endpoints, and does not execute tools.

Built-in compiler plans now expand multi-dependency packs into tool-level plan nodes when catalog contracts exist. A default `discover_assets` workspace plan emits separate nodes for `httpx`, `subfinder`, `amass`, `dnsrecon`, `dnsx`, `naabu`, and `nmap`, plus a pack-level `ctf-pack` fallback for `ctf.challenge_classification`. An explicit `fingerprint_surface` action can also emit `ctf.artifact_analysis` tool-level nodes such as `mobsfscan` from the app/artifact catalog, `generate_candidates` can emit URL-scoped `nuclei/template_scan`, `dalfox/xss_scan`, and `sqlmap/injection_test` nodes, and `enumerate_paths` can emit URL-scoped `ffuf/path_fuzz`, `katana/crawl`, and `arjun/parameter_discovery` plus domain-scoped `gau/archive_discovery` and `waybackurls/archive_discovery` route-enumeration nodes. Runtime worker artifacts keep the legacy top-level `tool` field as the manifest name for compatibility, while the nested `tool_plan` carries `tool_id`, `adapter_id`, `operation`, `parser_id`, `target_kind`, `dependency_name`, and `dependency_kind`. Worker and native command environments expose the same identity as `OURO_TOOL_ID`, `OURO_ADAPTER_ID`, `OURO_OPERATION`, `OURO_PARSER_ID`, `OURO_TARGET_KIND`, `OURO_DEPENDENCY_NAME`, and `OURO_DEPENDENCY_KIND`.

`nuclei` requires both a tool binary and the installed `nuclei-templates` rule bundle. In process isolation, `httpx`, `nmap`, `subfinder`, `amass`, `naabu`, `dnsx`, `dnsrecon`, `gau`, `waybackurls`, `ffuf`, `katana`, `dalfox`, `arjun`, and `sqlmap` require workspace-managed binaries before execution. In container isolation, the same registered managed argv builders are allowed to run through the command runner without resolving a host binary first, so the configured container image is responsible for providing the inner tool command. `naabu` only runs from CIDR scope. `subfinder`, `amass`, `dnsx`, `dnsrecon`, `gau`, and `waybackurls` run only from explicit domain scope and remain offline for URL-only, host-only, or CIDR-only scope; `ffuf`, `katana`, `dalfox`, `arjun`, and `sqlmap` run only from explicit URL scope and remain offline for domain-only, host-only, or CIDR-only scope. `apktool`, `jadx`, `semgrep`, `gitleaks`, `trufflehog`, `binwalk`, and `exiftool` remain catalog/registry entries only until their own builders, output handling, and parser/evidence boundaries are implemented. Unknown operations, unsupported tool/operation pairs, missing target context, missing binary dependency contracts, missing process-mode workspace-managed binaries, missing required rule bundles, invalid container configuration, and unsafe artifact paths still fail closed to the offline/error boundary instead of falling through to ambient host `PATH`. Additional app/artifact tool argv builders, parser dispatch beyond the current narrow promoted parser set, and real managed payload bundles remain separate implementation steps.

Converting a placement plan into ownership is explicit. `ExecuteRuntimeWorkerPlacementClaim` and `ouro runtime execute-worker-placement-plan <workspace> <plan> --execute [--execution-id <id>] [--worker <id>]` accept only dry-run metadata-only placement plans, select a ready candidate, revalidate the current registered worker state, and then create a metadata-only queue claim through the same `CreateRuntimeWorkerQueueClaim` path. The execution writes an audit artifact under `workspace/runtime/worker-placement-claim-executions/*.json`; stale/offline/capability-mismatched workers become skipped execution artifacts and do not create queue claims. `ouro runtime worker-placement-claim-executions <workspace> [execution]` lists or inspects those audits. Workspace-bound TUI Agent Runtime renders live placement summaries, placement-plan artifacts, and placement-claim execution rows; pressing `x` on a placement-plan artifact uses the same double-confirm pattern before creating a queue claim. This still does not dispatch, ack, contact endpoints, or execute tools.

Placement-derived dispatch planning is the next metadata-only review boundary. `PlanRuntimeWorkerPlacementDispatches` and `ouro runtime worker-placement-dispatch-plan <workspace> [--transport metadata-only|file-outbox|http-json]` read placement-claim execution audits plus their linked queue claims, revalidate whether those claims are still dispatch-ready, and persist a dry-run plan under `workspace/runtime/worker-placement-dispatch-plans/*.json`. `ouro runtime worker-placement-dispatch-plans <workspace> [plan]` lists or inspects those plans. Workspace-bound TUI Agent Runtime renders placement-dispatch plan rows. This planning step does not mutate queue claims, does not write queue-dispatch execution artifacts, does not acknowledge outbox requests, does not contact endpoints, and does not execute tools.

Executing a placement-derived dispatch plan is a separate explicit gate. `ExecuteRuntimeWorkerPlacementDispatch` and `ouro runtime execute-worker-placement-dispatch-plan <workspace> <plan> --execute [--claim <claim>] [--execution-id <id>] [--worker <id>] [--transport-token-env <env>] [--result-callback <url>]` accept only dry-run metadata-only placement-dispatch plans, select one ready candidate, revalidate that the linked queue claim is still dispatch-ready, and then delegate to the existing queue-dispatch gate. The execution writes an audit artifact under `workspace/runtime/worker-placement-dispatch-executions/*.json`; skipped claims become skipped audit artifacts and do not create another queue dispatch. `ouro runtime worker-placement-dispatch-executions <workspace> [execution]` lists or inspects those audits. The default transport remains metadata-only unless the plan selected `file-outbox` or `http-json`; `http-json` still requires the same explicit transport/auth/callback controls. Token lookup follows the persisted plan transport, so `metadata-only` and `file-outbox` execution skip `--transport-token-env` even when an env name is provided, while `http-json` reads bearer material only from the named env and never persists it. Workspace-bound TUI Agent Runtime renders placement-dispatch execution rows, and pressing `x` on a placement-dispatch artifact uses double confirmation before running this gate.

Multi-candidate placement dispatch orchestration is also explicit. `ExecuteRuntimeWorkerPlacementDispatchBatch` and `ouro runtime execute-worker-placement-dispatch-plan <workspace> <plan> --execute --all [--max-candidates <n>]` iterate ready candidates from one dry-run placement-dispatch plan, revalidate each claim before mutation, and call the same single-candidate dispatch gate for each candidate. Batch audits are written under `workspace/runtime/worker-placement-dispatch-batches/*.json`, while individual placement-dispatch execution and queue-dispatch artifacts remain the per-candidate source of truth. In the workspace-bound TUI, pressing `x` twice on a placement-dispatch artifact with more than one ready candidate runs this batch gate and surfaces the batch plus per-candidate audit rows.

Top-level worker orchestration is an audit composition layer over those same gates. `CreateRuntimeWorkerOrchestration` and `ouro runtime worker-orchestrate <workspace> [--run-id <run>] [--transport metadata-only|file-outbox|http-json] [--max-candidates <n>]` write a `workspace/runtime/worker-orchestrations/*.json` artifact. By default the artifact is `dry-run` / `metadata-only`: it records placement ready/skipped counts from a fresh placement preview, but it does not persist a placement plan, create queue claims, create dispatch plans, write dispatch executions, create outbox requests, contact endpoints, acknowledge requests, or execute tools. With `--execute`, the orchestration creates one placement-plan artifact, claims bounded ready candidates through `ExecuteRuntimeWorkerPlacementClaim`, creates a placement-dispatch plan, and runs the existing placement-dispatch batch gate. The default transport remains `metadata-only`; `file-outbox` and `http-json` still use the same explicit transport/auth/callback controls as queue dispatch. `--include-lifecycle-maintenance` is a separate non-default execution option that appends only metadata-only lifecycle maintenance and lifecycle audit artifacts after the placement/dispatch composition, linking those artifact paths back into the orchestration audit. Default lifecycle attachment still skips retry-dispatch execution. The narrower `--execute-lifecycle-retry-dispatches` flag requires both `--execute` and `--include-lifecycle-maintenance`; when enabled it passes the existing maintenance retry gate through the orchestration, records retry-dispatch execution counts/paths on the orchestration artifact, and creates metadata-only retry queue claims. Without the separate `--dispatch-lifecycle-retry-claims` flag, retry execution stops there. With `--dispatch-lifecycle-retry-claims --lifecycle-retry-transport metadata-only|file-outbox`, the newly created retry claims may only flow through the existing queue-dispatch gate as metadata-only queue-dispatch audits or pending file-outbox requests; `http-json` is rejected. The handoff still does not contact endpoints or targets, acknowledge requests, run worker commands or stored tool-plan commands, apply daemon controls, reclaim or release leases, submit results, or execute tools. `ouro runtime worker-orchestrations <workspace> [orchestration]` lists or inspects the top-level artifacts, and workspace-bound TUI Agent Runtime renders them as read-only rows whose `d` details open in Node Inspector. There is deliberately no TUI execution shortcut for orchestration artifacts, no auto-ack, no auto-approval, and no resident scheduler loop.

Runtime worker orchestration supervision repeats that top-level composition only inside an explicit bounded run. `CreateRuntimeWorkerOrchestrationSupervisor` and `ouro runtime worker-orchestration-supervisor <workspace>` write a dry-run `workspace/runtime/worker-orchestration-supervisor-runs/*.json` artifact by default and create no child orchestration, placement, claim, dispatch, outbox, lifecycle, or audit artifacts. `ouro runtime worker-orchestration-supervisor <workspace> --execute --max-runs <n> [--run-id-prefix <prefix>] [--transport metadata-only|file-outbox|http-json] [--max-candidates <n>] [--include-lifecycle-maintenance]` performs at most `n` child `CreateRuntimeWorkerOrchestration` passes, then stops. The default transport remains `metadata-only`; `file-outbox` and `http-json` still rely on the same explicit transport/auth/callback options as queue dispatch. `--include-lifecycle-maintenance` remains non-default and only links metadata-only maintenance/audit artifacts through each child orchestration. `ouro runtime worker-orchestration-supervisor <workspace> --execute --max-runs <n> --include-lifecycle-maintenance --execute-lifecycle-retry-dispatches` is the supervisor's narrower retry automation gate: it requires both parent gates, passes the existing lifecycle retry option into each child orchestration, aggregates `retry_dispatch_executions_created` and `retry_dispatch_claims_created`, and links retry-dispatch execution audit paths. The default supervisor lifecycle attachment still skips retry-dispatch execution; explicit retry execution creates retry-dispatch execution audits plus metadata-only retry queue claims and stops there unless `--dispatch-lifecycle-retry-claims --lifecycle-retry-transport metadata-only|file-outbox` is also present. That handoff may only create metadata-only queue-dispatch audits or pending file-outbox requests through the existing queue-dispatch gate, rejects `http-json`, and still does not contact endpoints or targets, acknowledge requests, run stored tool-plan commands, submit results, apply daemon controls, release or reclaim leases, run daemons, or execute tools. `ouro runtime worker-orchestration-supervisor-runs <workspace> [artifact]` lists or inspects the bounded supervisor audits, and workspace-bound TUI Agent Runtime renders them as read-only rows/details with compact retry-dispatch aggregate rows. The supervisor is not a resident scheduler and does not auto-ack, auto-approve, run worker commands, apply daemon controls, reclaim or release leases, contact endpoints, run daemons, submit results, or execute tools.

Runtime worker bounded CLI gates now reject invalid operator limits before they can create artifacts or run loops. `worker-transport-run-loop` requires `--max-requests > 0`; `worker-transport-run-daemon` and `worker-transport-run-supervisor` require positive `--max-requests`, `--idle-rounds`, and `--poll-interval-ms`, and the supervisor also requires `--max-runs > 0`; `worker-lifecycle-maintenance-supervisor` and `worker-orchestration-supervisor` require `--max-runs > 0`. This validation is CLI-side, so app-level zero values can still preserve internal default behavior while explicit invalid operator input fails closed.

HTTP receiver and hosted replay bounds use a non-negative rule instead of the positive worker-loop rule because `0` is the documented "run until interrupted" mode for local operators and tests. `replay-workbench --max-requests`, `worker-transport-serve-http --max-requests`, and `worker-queue-dispatch-result-serve-http --max-results` now reject negative values before replay loading, token lookup, listener creation, request handling, artifact writes, endpoint contact, dispatch, result submission, or tool execution.

Runtime-worker safety-bypass authorization is now enforced at twelve direct app side-effect gates: `ExecuteRuntimeWorkerQueueClaimDispatch`, worker-side HTTP receive/artifact ingress through `NewRuntimeWorkerTransportHTTPHandler` / `worker-transport-serve-http`, `CreateRuntimeWorkerTransportDaemonControlRequest` / `worker-transport-daemon-control` when writing pending daemon stop/restart control requests, `AcknowledgeRuntimeWorkerTransportDispatchRequest`, `ExecuteRuntimeWorkerTransportDispatchRequest`, `SubmitRuntimeWorkerQueueDispatchResult`, `ExecuteRuntimeWorkerDispatchRetryDispatch`, `UpdateWorkerLeaseHeartbeat`, `ReleaseWorkerLease`, `ExecuteWorkerLeaseReclaimDispatch`, `ExecuteWorkerLeaseResultReconciliationDispatch`, and `ExecuteRuntimeWorkerTransportDispatchDaemon` when `--enable-control` consumes pending daemon stop/restart controls. When `scope.target_policy` or `execution.isolation` is disabled without current matching `authorization.yaml` metadata, those gates fail before queue dispatch mutation or endpoint contact, accepted HTTP receive file-outbox artifact writes, pending daemon-control request creation, file-outbox request acknowledgement, worker request-command execution, worker queue dispatch result submission, retry-claim creation, active-lease heartbeat writes, active-lease release writes, stale-lease reclaim writes/execution audits, reconciliation release writes/execution audits, or pending daemon-control consumption, applied-status writes, and daemon audit control metadata. Worker-side HTTP receive validates bearer token, worker id, and transport mode before the safety preflight, so missing or wrong bearer tokens return `401` responses without safety details; accepted receives write pending file-outbox artifacts only with current authorization under disabled boundaries. Daemon-control creation validates worker id/action before the safety preflight and writes pending metadata-only control artifacts only with current authorization under disabled boundaries. Higher-level loop, daemon, supervisor, orchestration, maintenance, and scheduler commands inherit that check only when they delegate through one of those gates; the supervisor inherits daemon-control protection through child daemon runs and is not counted as another direct gate.

Result-callback HTTP is not counted separately; `NewRuntimeWorkerQueueDispatchResultHTTPHandler` / `worker-queue-dispatch-result-serve-http` accepts callbacks into `SubmitRuntimeWorkerQueueDispatchResult` and inherits that submission preflight. List/read, daemon-control list/read, and metadata-only planning/review paths keep their existing boundaries. Ordinary run lease acquire/complete writes are outside this runtime-worker direct gate list, but strict `ouro run --require-safety-authorization` now rechecks current authorization before those lease writes; default runs remain warning-only.

Runtime worker queue claim metadata is stored under `workspace/runtime/worker-queue-claims/*.json`. `ouro runtime worker-queue-claim <workspace> <worker> --run-id <run> --execution-id <execution> --tool <tool> --capability <capability>` writes a `status: claimed`, `mode: metadata-only` claim with lease timestamps after revalidating that the registered worker exists, is not offline or stale, and advertises the requested capability. Queue claims can also carry first-pass structured tool-plan payload through `--action`, `--runner`, `--parser`, repeated `--run-command`, `--run-timeout-ms`, repeated `--input-node`, and repeated `--expected-evidence`; app-created claims can set the same `tool_plan` JSON payload directly. `ouro runtime worker-queue-claims <workspace>` lists claims, and `ouro runtime worker-queue-claims <workspace> <claim>` inspects one by basename or workspace-confined path. `ouro runtime worker-queue-claim-cancel <workspace> <claim> --cancel [--canceled-by <operator>] [--reason <text>]` explicitly releases a still-claimed artifact by rewriting only that claim to `status: canceled` with `canceled_at`, `canceled_by`, and `cancel_reason`; it rejects already dispatched/completed/canceled claims and writes no dispatch audit, outbox request, endpoint call, worker mutation, or tool execution. `ouro runtime worker-queue-claim-expire <workspace> <claim> --expire [--expired-by <operator>] [--reason <text>]` marks a still-claimed artifact whose `expires_at` has elapsed as `status: expired`, recording `expired_at`, `expired_by`, and `expire_reason` with the same no-execution invariant. `ouro runtime worker-queue-claim-renew <workspace> <claim> --renew --lease-seconds <n> [--renewed-by <operator>] [--reason <text>]` extends only still-claimed, unexpired artifacts, rewriting `renewed_at`, `renewed_by`, `renew_reason`, `lease_seconds`, and `expires_at` while preserving the no-execution invariant. Workspace-bound TUI Agent Runtime renders queue-claim summary, compact rows with `metadata-only` visible in normal widths, canceled/expired/renewed counts and metadata, and tool-plan action/runner/parser/command rows when present. Uppercase `C`, `E`, and `L` use double confirmation for cancel, expire, and renew, respectively.

Dispatching a queue claim is an explicit gate. `ouro runtime execute-worker-queue-claim <workspace> <claim> --execute` is required before a claim can move from `claimed` to `dispatched`; without `--execute` it returns an error and writes no audit artifact. The gate re-reads the claim and registered worker, rejects expired/non-claimed/non-metadata claims, skips stale/offline/capability-mismatched workers with an audit reason, and writes `workspace/runtime/worker-queue-dispatch-executions/*.json`. The default transport is `metadata-only`; `--transport file-outbox` writes a request JSON under `workspace/runtime/worker-transport-outbox/<worker-id>/`, records that request path on the dispatch audit, and copies the claim's `tool_plan` payload into both the dispatch audit and file-outbox request. `--transport http-json` is the first explicit network dispatch adapter: it requires the registered worker endpoint to be `http` or `https`, POSTs the same request JSON, records endpoint/status/response metadata on the dispatch audit, and leaves final completion to the same result-return API. When `--transport-token-env <env>` is provided, the sender reads a bearer token from that environment variable, sends it as `Authorization: Bearer ...`, and records only `transport_auth: bearer` in the dispatch audit; the secret is not printed or persisted. On the worker side, `ouro runtime worker-transport-serve-http <workspace> <worker> --execute --listen <addr>` receives those `http-json` requests and persists them as pending file-outbox request artifacts. `--auth-token-env <env>` makes the receiver require the matching bearer token before decoding, safety preflight, or writing a request, while omitting the flag keeps a deliberate no-auth compatibility/testing path. The receiver validates bearer token, worker id, and transport mode before the safety preflight, so missing or wrong bearer tokens return `401` without exposing safety details; when target policy or isolation is disabled, accepted receives write pending file-outbox artifacts only with current safety-bypass authorization. `--max-requests <n>` gives tests and supervised runs a bounded exit. `ouro runtime worker-queue-dispatch-executions <workspace>` lists those audits, and `ouro runtime worker-queue-dispatch-executions <workspace> <execution>` inspects one by basename or workspace-confined path. `ouro runtime worker-transport-outbox <workspace> <worker> [request]` lists or inspects the file-outbox requests for one worker, and `ouro runtime worker-transport-ack <workspace> <worker> <request> --ack` explicitly moves a pending request to `acknowledged` without executing the tool; that ack gate also requires current safety-bypass authorization when target policy or isolation is disabled. `ouro runtime worker-transport-run-once <workspace> <worker> <request> --execute -- <command> [args...]` executes one acknowledged request with an operator-supplied command from a workspace-confined runtime working directory; alternatively `--use-request-command` executes the request's stored `tool_plan.run_command` without a separate command. `ouro runtime worker-transport-run-loop <workspace> <worker> --execute --max-requests <n> -- <command> [args...]` repeats one operator command for up to `n` acknowledged requests; with `--use-request-command`, it executes each request's own stored `tool_plan.run_command`. `ouro runtime worker-transport-run-daemon <workspace> <worker> --execute --max-requests <n> --idle-rounds <n> --poll-interval-ms <ms>` repeatedly polls the same outbox, executes newly appearing acknowledged requests through the same loop/result-return path, and exits after the processed-request or idle-round limit. Each daemon execution writes a run audit artifact under `workspace/runtime/worker-transport-daemon-runs/<worker-id>/`, recording status, scan counts, source mode, result paths, control metadata, and errors without persisting operator command arguments; `ouro runtime worker-transport-daemon-runs <workspace> <worker> [run]` lists or inspects those artifacts. `ouro runtime worker-transport-daemon-control <workspace> <worker> --action stop|restart [--reason <text>] [--requested-by <operator>]` writes a pending metadata-only control request under `workspace/runtime/worker-transport-daemon-controls/<worker-id>/` after worker id/action validation and, when target policy or isolation is disabled, current safety-bypass authorization; `ouro runtime worker-transport-daemon-controls <workspace> <worker> [control]` lists or inspects those requests without requiring that gate. Daemons ignore pending control requests by default; `worker-transport-run-daemon --enable-control` is the explicit opt-in that consumes the first pending stop/restart request before starting more work, writes `stopped` or `restart-requested` daemon audit metadata, and marks the control request `applied`. That control-consumption branch reuses the runtime-worker safety authorization preflight when target policy or isolation is disabled, before it records stopped/restart-requested daemon audit metadata or rewrites the pending control request to `applied`; daemon-control list/read remain metadata-only and do not require that gate. `ouro runtime worker-transport-run-supervisor <workspace> <worker> --execute --max-runs <n> --max-requests <n> --idle-rounds <n> [--enable-control]` composes bounded daemon runs and writes `workspace/runtime/worker-transport-daemon-supervisor-runs/<worker-id>/*.json`; a supervised daemon restart is acted on only when `--enable-control` is present, `stop` ends the supervisor, and repeated restart requests stop at `restart-limit` instead of looping forever. The supervisor inherits the same daemon-control safety check only through child daemon runs with `--enable-control`; `ExecuteRuntimeWorkerTransportDaemonSupervisor` is not a separately counted direct gate. `ouro runtime worker-transport-supervisor-runs <workspace> <worker> [run]` lists or inspects those supervisor audits. The HTTP receiver, daemon, and supervisor do not auto-ack pending requests. All worker execution paths inject only `PATH` plus `OURO_*` request context variables, including `OURO_ACTION`, `OURO_MANIFEST_NAME`, `OURO_RUNNER`, `OURO_PARSER`, `OURO_RUN_COMMAND_JSON`, `OURO_INPUT_NODE_IDS_JSON`, `OURO_EXPECTED_EVIDENCE_JSON`, and `OURO_TOOL_PLAN_JSON`, and submit completed/failed results through the same result-return API. Workspace-bound TUI Agent Runtime shows dispatch audit rows, file-outbox request paths, HTTP endpoint/status/response rows for `http-json`, daemon run rows, daemon supervisor rows, daemon control request rows, compact worker transport request status counts, canceled/expired queue-claim rows, and tool-plan rows when present. Pressing `d` on a daemon control artifact or daemon supervisor artifact opens read-only Node Inspector details for artifact path, worker, status, mode, and relevant control/source metadata. Pressing `x` on a queue-claim artifact follows the same double-confirm pattern before calling the dispatch app gate; pressing `C` twice on the same kind of row calls the cancel gate, writes only canceled metadata to the claim, and does not create dispatch audits, outbox requests, endpoint calls, or tool executions. Pressing `E` twice on an expired queue-claim artifact calls the expire gate and writes only expired metadata with the same non-execution invariant. Pressing `x` twice on a pending worker transport request row calls the same ack gate and only moves that request to `acknowledged`; it does not execute the request, run a daemon, or submit a result. Pressing `x` twice on an already acknowledged worker transport request row calls the existing run-once execution gate with `--use-request-command` semantics, so only the request's stored `tool_plan.run_command` is executed and the result is submitted through the same result-return API. Pressing `R` twice on the same daemon artifact writes a pending metadata-only `restart` control request through that same creation gate. Actual stop/restart consumption still requires launching the daemon with `--enable-control` or the supervisor with `--enable-control`. This records auditable dispatch intent and consumes the claim metadata; `file-outbox` gives external worker processes a polling, ack, run-once, bounded-loop, resident-daemon, daemon-run audit, daemon supervisor audit, daemon control request, and request-carried tool-plan execution contract without opening a network connection from the IDE process, while `http-json` opens one only after the explicit `--execute --transport http-json` operator gate and lands back into the same explicit ack boundary.

Worker result return is also artifact-first. `ouro runtime worker-queue-dispatch-result <workspace> <execution> --status completed|failed [--output <summary>] [--error <summary>]` submits the result for an already-dispatched queue execution, writes `workspace/runtime/worker-queue-dispatch-results/*.json`, updates the dispatch execution status to `completed` or `failed`, closes the original queue claim with `result_status`, `result_path`, and `completed_at`, and closes a linked file-outbox request with the same final status when one exists. Audit planning and artifact creation write only the optional lifecycle-audit report itself; they do not create policy-runs, scheduler-runs, supervisors, queue claims, outbox requests, endpoint/transport/target contact, acknowledgements, result submissions, lease mutations, run daemons, or execute tools.

Worker lifecycle audit also mirrors action-plan review state as read-only reporting metadata. It reads existing worker lifecycle action-plan artifacts, their `accepted` / `deferred` / `rejected` annotation metadata, and the current/cleared `workspace/runtime/worker-lifecycle-action-plan-selection.json` marker as audit items and counts only. CLI and TUI audit rows now surface `action_plan_annotations`, `action_plan_selections`, review decision/reviewer/time, selection or clear actor/time, and compact marker rows for normal panel widths. Audit planning and `--write` artifact creation still write only the optional lifecycle-audit report; they do not annotate action plans, select or clear the marker, consume recommendations, create maintenance artifacts, acknowledge or run transport requests, execute retry-dispatch artifacts, create queue claims, mutate leases, apply daemon controls, contact endpoints or targets, append replay events, submit results, or execute tools.

Worker lifecycle policies are metadata-only strategy input for explicit policy-run execution. `PreviewWorkerLifecyclePolicy` and `ouro runtime worker-lifecycle-policy <workspace>` produce a dry-run policy from the current lifecycle audit summary; `--write` persists metadata-only JSON under `workspace/runtime/worker-lifecycle-policies/`. The policy records stale lease and worker-registration thresholds, poll interval metadata, max supervisor runs, planned transport, lifecycle-maintenance inclusion, lifecycle-retry intent, default-off lifecycle retry handoff intent, default-off lifecycle lease-recovery intent, and current worker/lease/retry/audit counts. `--dispatch-lifecycle-retry-claims` is accepted only with `--include-lifecycle-maintenance` and `--execute-lifecycle-retry-dispatches`; its separate `--lifecycle-retry-transport` accepts only `metadata-only` or `file-outbox`, rejects `http-json`, and records default-off policy intent consumed only by explicit policy-run/scheduler-run paths. `--execute-lifecycle-lease-recovery` is accepted only with `--include-lifecycle-maintenance`; it records default-off policy intent consumed only by explicit policy-run/scheduler-run paths and does not mutate leases by itself. `ListWorkerLifecyclePolicies`, `ReadWorkerLifecyclePolicy`, and `ouro runtime worker-lifecycle-policies <workspace> [artifact]` list or inspect persisted policies by basename or workspace-confined path. `SelectWorkerLifecyclePolicy` / `ouro runtime worker-lifecycle-policy-select <workspace> <artifact>` write the closeable current marker at `workspace/runtime/worker-lifecycle-policy-selection.json` with `status=current`, making the artifact the current strategy input; `ReadWorkerLifecyclePolicySelection` / `ouro runtime worker-lifecycle-policy-selection <workspace>` read the marker; and `ClearWorkerLifecyclePolicySelection` / `ouro runtime worker-lifecycle-policy-selection-clear <workspace>` rewrite the same marker to `status=cleared`, explicitly disabling current strategy/focus without deleting audit context. Workspace-bound TUI Agent Runtime uses double-confirm `x` to select a non-current policy artifact or clear a current selection, and writes only that marker JSON. Invalid bounds, unsupported transports, and lifecycle retry, lifecycle retry handoff, or lease-recovery policy without lifecycle maintenance are rejected before writing artifacts. Policy artifacts and selection markers are strategy metadata only: poll interval is not a scheduler loop, default Ouroboros starts no resident lifecycle scheduler, and these paths have no supervisor, maintenance, queue-claim, transport, endpoint, target, execution artifact, lease, result, or tool side effects.

Worker lifecycle policy runs are the explicit, bounded bridge from a selected strategy marker into lifecycle maintenance supervision. `CreateWorkerLifecyclePolicyRun` and `ouro runtime worker-lifecycle-policy-run <workspace> [--execute]` read only the current selection marker at `workspace/runtime/worker-lifecycle-policy-selection.json`; the marker must exist with `status=current`, and missing or cleared markers fail closed before policy-run artifact writes or child gates. A default run writes a metadata-only policy-run audit artifact under `workspace/runtime/worker-lifecycle-policy-runs/` and creates no supervisor, maintenance, queue, transport, request, result, lease, or tool side effects. `ouro runtime worker-lifecycle-policy-run <workspace> --execute` creates at most one maintenance supervisor using the selected policy's `MaxSupervisorRuns`, `StaleAfterSeconds`, `ExecuteLifecycleRetries`, `DispatchLifecycleRetryClaims`, `LifecycleRetryTransportMode`, and `ExecuteLeaseRecovery`; if the selected policy disables lifecycle maintenance, it writes a completed/skipped policy-run audit artifact with skip reason `lifecycle-maintenance-disabled` and no supervisor. Lifecycle retry handoff remains subordinate to the selected policy's explicit lifecycle retry execution gate: without the selected handoff flag it stops at metadata-only retry queue claims; with the selected handoff flag it may only create metadata-only queue-dispatch audits or pending file-outbox requests through the existing queue-dispatch gate. `ListWorkerLifecyclePolicyRuns`, `ReadWorkerLifecyclePolicyRun`, and `ouro runtime worker-lifecycle-policy-runs <workspace> [artifact]` list or inspect those policy-run audits. Workspace-bound TUI Agent Runtime renders policy-run artifacts as read-only visibility rows/Inspector details with no TUI shortcut to run them yet. The policy runner is not a resident scheduler: it does not sleep, tick, start a background goroutine, repeat invocation, contact endpoints, contact targets, contact transports, acknowledge requests, execute stored tool-plan commands, submit results, apply daemon controls, or execute tools beyond the existing explicit child gates.

The scheduler-run layer stays a bounded policy-run launcher, not a resident scheduler. `ouro runtime worker-lifecycle-policy-scheduler-run <workspace> [--execute --max-runs N]` reads only the current `runtime/worker-lifecycle-policy-selection.json` marker, requires `status=current`, and revalidates the selected policy artifact before writing. Without `--execute`, it writes one metadata-only dry-run scheduler audit under `workspace/runtime/worker-lifecycle-policy-scheduler-runs/` and creates no child policy-run or supervisor artifacts. With `--execute`, it requires a positive `--max-runs`, creates at most that many policy-run children through the existing policy-run gate, and stops without sleep/ticker/background scheduling. Lease recovery and lifecycle retry handoff automation remain default-off: scheduler execution may release/reclaim leases only when the selected policy's explicit recovery gate is enabled, and may hand off retry claims only when the selected policy enables lifecycle maintenance, lifecycle retry execution, and lifecycle retry handoff with `metadata-only` or `file-outbox` transport. A cleared policy marker or `poll_interval_ms=0` is the close/off path and creates no recovery or retry-handoff children. Missing, cleared, empty, invalid, or tampered selections, invalid selected policy bounds, unsupported transports, negative poll intervals, and negative dry-run `--max-runs` fail closed before writes. `ouro runtime worker-lifecycle-policy-scheduler-runs <workspace> [artifact]` lists or inspects scheduler-run audits. Workspace-bound TUI Agent Runtime renders scheduler-run rows read-only; `d` opens Inspector details only, while `x` and `r` remain unsupported for execution or request creation. The scheduler-run safety invariant is no endpoint, target, or transport contact; no acknowledgement; no stored tool command execution; and no result submission. The only enabled retry handoff side effect is an explicit metadata-only queue-dispatch audit or pending file-outbox request.

Worker lifecycle action plans are an explicit recommendation layer over that review state, not an execution shortcut. `PlanWorkerLifecycleActionPlan` and `ouro runtime worker-lifecycle-action-plan <workspace> [review]` derive ready operator gates for pending file-outbox acknowledgement, acknowledged request run-once execution, pending daemon stop/restart control consumption, persisted ready worker retry-dispatch execution, stale lease reclaim review, and lease/result reconciliation review. Pending daemon controls are shown as `apply-daemon-control` recommendations with the explicit `worker-transport-run-daemon-enable-control` gate; this is guidance to launch a daemon or supervisor with `--enable-control`, not a control consumer. Persisted worker retry-dispatch artifacts with ready candidates are shown as `execute-dispatch-retry-dispatch` recommendations with the explicit `worker-dispatch-retry-dispatch-execute` gate, but already executed retry-dispatch artifacts are not recommended again. `ouro runtime worker-lifecycle-action-plan <workspace> [review] --write` persists the recommendations as dry-run metadata-only JSON under `workspace/runtime/worker-lifecycle-action-plans/`, and `ouro runtime worker-lifecycle-action-plans <workspace> [artifact]` lists or inspects those artifacts. Workspace-bound TUI Agent Runtime shows only explicitly written action-plan artifacts, compact counts, per-action rows, short daemon-control recommendation rows, and short retry-dispatch action rows; selecting a `worker lifecycle action:` row and pressing `d` opens read-only Inspector details for the recommended gate, worker/run/execution identity when present, reason, request/lease/result/dispatch paths, and recommended status. Automatic recommendation rows still do not render, so queue/transport/lease/retry facts stay visible. Action-plan creation and inspection do not acknowledge requests, run requests, execute retry-dispatch artifacts, apply daemon controls, create queue claims, create reclaim or reconciliation dispatches, release or reclaim leases, contact endpoints, run daemons, submit results, or execute tools.

Worker lifecycle action-plan review now has the same auditable closeable focus boundary as report review and lifecycle policy selection. `ouro runtime worker-lifecycle-action-plan-annotate <workspace> <artifact>` rewrites only the selected workspace-confined action-plan JSON with `accepted`, `deferred`, or `rejected` reviewer metadata; `false-positive` is deliberately rejected as a decision value, so authorized false-positive state should be recorded as `rejected` plus `reason`. `worker-lifecycle-action-plan-select` writes `workspace/runtime/worker-lifecycle-action-plan-selection.json` with `status=current` only for a version 1 `dry-run` / `metadata-only` action-plan annotated `accepted`; `worker-lifecycle-action-plan-selection` reads that marker, and `worker-lifecycle-action-plan-selection-clear` rewrites the same marker to `status=cleared` without deleting audit context. CLI selection output derives `current=true|false` from marker status and prints explicit `selection_path`, `plan_path`, and `review_path` labels while retaining the compact aliases. Workspace-bound TUI Agent Runtime surfaces annotation/review rows plus current/cleared marker rows; Inspector details use `selection status`, `plan path`, `selection path`, and `review path`, and action-plan artifact details label review JSON as a review path instead of a dispatch path. Double-confirm `x` can only select a noncurrent accepted action-plan artifact or clear the current marker as metadata-only. Symlinked action-plan files and symlinked selection markers are rejected before writes. These review, select, clear, and display paths do not acknowledge or run requests, execute retry-dispatch artifacts, create queue claims, create maintenance artifacts, mutate leases, apply daemon controls, contact endpoints or targets, submit results, append replay events, or execute tools.

Worker lifecycle maintenance is a bounded metadata-only composition gate for recovery review preparation. `ouro runtime worker-lifecycle-maintenance <workspace>` writes a dry-run audit under `workspace/runtime/worker-lifecycle-maintenance/` with the current action counts but creates no child artifacts. `ouro runtime worker-lifecycle-maintenance <workspace> --execute` creates one lifecycle review, one lifecycle action plan, and only metadata-only stale-lease reclaim / lease-result reconciliation review artifacts when the action plan has ready recovery actions. Default maintenance still skips lease recovery execution as `requires-explicit-operator-gate`. Only the non-default `--execute --execute-lease-recovery` flag may invoke the existing lease reclaim / lease-result reconciliation execution gates, and it must not dispatch claims, write outbox requests, contact endpoints or targets, acknowledge requests, run commands, submit results, apply daemon controls, or execute tools. By default it also records ack, run-once, daemon-control, and worker retry-dispatch execution recommendations as skipped with `requires-explicit-operator-gate`; retry-dispatch execution is counted as `retry_dispatch_execute` and surfaced in CLI/TUI maintenance rows. `ouro runtime worker-lifecycle-maintenance <workspace> --execute --execute-retry-dispatches` remains a separate non-default retry automation gate that creates retry-dispatch execution audits plus metadata-only retry queue claims; without the handoff flag, retry execution stops there. The extra `--dispatch-lifecycle-retry-claims --lifecycle-retry-transport metadata-only|file-outbox` handoff is subordinate to that retry gate, rejects `http-json`, and may create only metadata-only queue-dispatch audits or pending file-outbox requests. Handoff without `--execute` or `--execute-retry-dispatches` fails before maintenance writes. CLI output and TUI Agent Runtime rows surface retry counts, retry handoff counts, lease recovery execution/result counts, and linked execution/request paths. `ouro runtime worker-lifecycle-maintenances <workspace> [artifact]` lists or inspects those audits, and workspace-bound TUI Agent Runtime renders compact maintenance rows plus read-only `d` Inspector details. Maintenance never acknowledges requests, runs file-outbox commands, applies daemon controls, contacts endpoints or targets, runs daemons, submits results, or executes tools.

Worker lifecycle maintenance supervision is bounded and still metadata-only by default. `ouro runtime worker-lifecycle-maintenance-supervisor <workspace>` writes a dry-run run artifact under `workspace/runtime/worker-lifecycle-maintenance-supervisor-runs/` and creates no child artifacts. `ouro runtime worker-lifecycle-maintenance-supervisor <workspace> --execute --max-runs <n>` performs at most `n` maintenance passes; each pass creates only a metadata-only lifecycle maintenance artifact and a metadata-only lifecycle audit artifact, then stops. Supervisor summaries aggregate child maintenance action counts, skipped-unsafe counts, retry-dispatch counts, retry handoff counts, and lease-recovery execution/result counts. `--execute-lease-recovery` passes the explicit lease recovery option into child maintenance and is rejected without `--execute`; `--execute-retry-dispatches` remains the separate retry-dispatch automation gate. `--dispatch-lifecycle-retry-claims --lifecycle-retry-transport metadata-only|file-outbox` can further hand newly created retry claims to the existing queue-dispatch gate and aggregate dispatched/request counts, but only with `--execute` and `--execute-retry-dispatches`. Handoff rejects `http-json`; even when enabled, these supervisor gates do not contact endpoints or targets, acknowledge requests, run stored tool-plan commands, submit results, apply daemon controls, mutate leases, run daemons, or execute tools. Pending file-outbox requests still require the existing ack/run/result-return gates. `ouro runtime worker-lifecycle-maintenance-supervisor-runs <workspace> [artifact]` lists or inspects those bounded run audits, and workspace-bound TUI Agent Runtime renders them above lower-level maintenance history with compact aggregate/execution rows and read-only `d` Inspector details. The supervisor is not a resident scheduler.

Worker lease/result reconciliation is a read-only convergence view. `PlanWorkerLeaseResultReconciliation` and `ouro runtime worker-lease-result-reconcile <workspace>` compare returned dispatch-result artifacts with matching worker leases by run id and execution id. A returned `completed` or `failed` result with a still-`active` lease is shown as a `metadata-only` ready candidate with a recommended release status; aligned leases and missing leases are reported as skipped. `ouro runtime worker-lease-result-reconcile <workspace> --write` persists the same review as a dry-run metadata-only JSON artifact under `workspace/runtime/worker-lease-result-reconciliations/`, and `ouro runtime worker-lease-result-reconciliations <workspace> [artifact]` lists or inspects those artifacts by basename or workspace-confined path. `ouro runtime execute-worker-lease-result-reconciliation <workspace> <artifact> --execute [--released-by <id>] [--reason <text>]` is the CLI mutation path from that review artifact: it refuses to run without `--execute`, accepts only dry-run metadata-only review artifacts, re-reads the current result and lease, applies the current safety-bypass authorization preflight when target policy or isolation is disabled, releases only still-`active` matching leases to the returned `completed` or `failed` status, skips already-closed or mismatched candidates, and writes audit JSON under `workspace/runtime/worker-lease-result-reconciliation-executions/`. `ouro runtime worker-lease-result-reconciliation-executions <workspace> [execution]` lists or inspects those audits. Workspace-bound TUI Agent Runtime surfaces ready reconciliation rows near the top of Agent Runtime, renders persisted review/execution artifacts with compact `result`, `lease`, `recommended`, state, and path rows, and can execute a selected persisted review only through the same app gate after a two-step `x` confirmation. The TUI shortcut writes the same execution audit, prepends the resulting audit rows for immediate review, and lets `d` open read-only details for the execution artifact. None of the review paths submit results, reclaim leases, dispatch claims, contact endpoints, or execute tools; the execution gate only calls the existing active-lease release transition after revalidation.

Worker runtime lease artifacts are written under `workspace/runtime/worker-leases/<run-id>/<execution-id>.json` for every started tool worker. Acquisition uses an atomic create and refuses to overwrite an existing active lease for the same run/execution id. A lease is first written with `status: active` plus `heartbeat_at`, then rewritten to `completed` or `failed` with release metadata after the runner returns. Workspace-bound TUI models list those artifacts in Agent Runtime so completed or failed workers remain inspectable even outside a live replay stream. Active leases older than the local stale threshold are rendered as `stale` in Agent Runtime. `ouro runtime worker-lease-heartbeat <workspace> <run-id> <execution-id> --heartbeat [--heartbeat-by <id>] [--reason <text>]` refreshes only an active lease's heartbeat metadata and optional operator context; it rejects missing `--heartbeat` and non-active leases, applies the current safety-bypass authorization preflight when target policy or isolation is disabled, does not release the lease, and does not create reclaim, dispatch, outbox, endpoint, or execution artifacts. Agent Runtime renders heartbeat `at/by/reason` rows so long-running external workers can keep a lease fresh before reclaim review. `ouro runtime worker-lease-release <workspace> <run-id> <execution-id> --release --status completed|failed [--released-by <id>] [--reason <text>] [--error <text>] [--result-execution-id <id>] [--attempt-dir <path>]` explicitly closes only an active lease as completed or failed. It rejects missing `--release`, unsupported statuses, and already closed/reclaimed leases; when disabled boundaries are configured it applies the same current safety-bypass authorization preflight before updating only the lease artifact's release/result metadata, and it does not create reclaim, dispatch, outbox, endpoint, or tool execution artifacts. Agent Runtime renders release `at/by/reason` rows plus linked result ids. Stale active leases also enter a metadata-only reclaim plan visible in Agent Runtime; this is an operator review boundary and does not mutate, reclaim, or restart workers. `ouro runtime worker-lease-reclaim <workspace>` persists that stale-lease plan as a dry-run metadata-only JSON artifact under `workspace/runtime/worker-lease-reclaims/`. `ouro runtime worker-lease-reclaims <workspace>` lists those artifacts, and `ouro runtime worker-lease-reclaims <workspace> <dispatch>` inspects one by basename or workspace-confined path. `ouro runtime execute-worker-lease-reclaim <workspace> <dispatch> --execute` is the explicit execution gate: it refuses to run without `--execute`, accepts only dry-run metadata-only reclaim artifacts, applies the current safety-bypass authorization preflight when target policy or isolation is disabled, revalidates each ready lease as still stale and active, marks only those leases `reclaimed`, skips refreshed or non-active leases, and writes audit JSON under `workspace/runtime/worker-lease-reclaim-executions/`. `ouro runtime worker-lease-reclaim-executions <workspace>` lists those audits, and `ouro runtime worker-lease-reclaim-executions <workspace> <execution>` inspects one by basename or workspace-confined path. Workspace-bound TUI models show existing reclaim artifacts and execution audit artifacts in Agent Runtime. Pressing `x` on a dry-run reclaim artifact in the TUI follows the same double-confirm pattern: the first press arms confirmation, and the second press calls the same app execution gate. These artifacts are a durable state boundary for future distributed workers; remote dispatch is not implemented yet.

## Adding Domain Packs

Add a new pack under `internal/domain/<name>/` with:

- `pack.go`: implements `domain.Pack` with capabilities, coverage dimensions, parser specs, and strategy patterns.
- `hypotheses.go`: converts typed `domain.Target` values into initial hypotheses.
- `pack_test.go`: validates pack contracts, accepted target kinds, rejected target kinds, and hypothesis coverage.

If the new pack has a workspace/runtime toolchain, add a matching manifest under `toolchains/<name>/manifest.yaml` and update workspace-local manifest templates in `internal/app/workspace.go`.

## Adding Tool Manifests

Tool manifests live at:

```text
toolchains/<pack>/manifest.yaml
```

Each manifest must declare `name`, `version`, `capabilities`, `runner`, `parser`, and `healthcheck`. Capabilities should match Domain Pack capability names exactly; the Tool Compiler routes semantic actions through these capability names.

Use `healthcheck: built_in` for bundled manifest readiness. Use `healthcheck: exec` plus a `health_command` array when a pack needs to probe an external binary:

```yaml
healthcheck: exec
health_command:
  - nuclei
  - -version
```

Exec health commands are run directly without a shell. The first non-empty output line becomes the installed version shown by `ouro toolchain health`.

Manifests can also declare runtime dependencies. Dependencies are checked separately from the manifest healthcheck, and required missing/failed dependencies downgrade the pack health. Omit `kind` for a binary dependency; set `optional: true` for non-blocking helpers:

```yaml
dependencies:
  - name: runtime-base
    kind: binary
    install_command:
      - ouro-toolchain
      - install
      - runtime-base
  - name: httpx
    kind: binary
    version: "1.3.0"
    depends_on:
      - runtime-base
    health_command:
      - httpx
      - -version
    install_hint: install a workspace-managed httpx payload
    install_command:
      - ouro-toolchain
      - install
      - httpx
```

`depends_on` references other dependency names in the same manifest. The manifest validator rejects empty references, unknown references, self-dependencies, duplicate dependency names, and dependency cycles. `install_command` is install-plan metadata only. Ouroboros prints it when a dependency is missing or failed, topologically orders unresolved prerequisites before dependents, and carries `depends_on` metadata into install requests and dispatch plans, but it does not execute the command automatically.

Container-image dependencies must pin a digest unless they are explicitly optional. `latest_version`, `source`, and `image_digest` are shown in dependency health output, which gives the operator update and provenance context before running tools:

```yaml
dependencies:
  - name: ouro-httpx-worker
    kind: container_image
    version: "1.0.0"
    latest_version: "1.1.0"
    source: ghcr.io/ouroboros/httpx-worker
    image_digest: sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

Dependencies can also declare `metadata_source` to fetch update metadata from a local fixture file, `file://` URL, or HTTP(S) endpoint. Relative file paths are resolved from the manifest directory. The metadata document can provide `latest_version`, `image_digest`, `source`, and `message`; a different latest version or digest marks the dependency `update_available` without downgrading pack readiness:

```yaml
dependencies:
  - name: ouro-httpx-worker
    kind: container_image
    version: "1.0.0"
    source: ghcr.io/ouroboros/httpx-worker
    image_digest: sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
    metadata_source: updates/httpx-worker.json
```

When a `container_image` dependency also declares a `health_command`, the first non-empty output line must include the declared `image_digest`. This lets a workspace use a fake or real container runtime inspect command in tests and production health checks; a digest mismatch marks the dependency failed.

`ouro toolchain health <workspace>` prints the pack health row, dependency rows, remote latest digest/source metadata, and deterministic `install:` plan rows for missing or failed dependencies that declare install metadata, so missing required tools and available updates are visible before a run starts without triggering automatic installation. Run/replay events carry the same install-plan rows, and the TUI Toolchain Health tab renders them as remediation hints.

`toolchain.BuiltInAppSecTools()` is the tool-level catalog for built-in Web/API, Infra/Internal, and APK/mobile/artifact tool metadata. Each executable catalog entry declares its pack, manifest dependency, dependency kind, target kind, adapter id, operation id, parser id, category, and capabilities. Manifest dependencies in `toolchains/*/manifest.yaml` must map back to catalog entries, catalog capabilities must be declared by the owning pack manifest, and `InitWorkspace` workspaces must produce manifests that match the bundled manifests. This catalog is metadata for planning and validation; it does not by itself execute a binary or imply that every listed payload is packaged.

Model-authored native tools use a strict structured spec, not shell snippets. `ouro toolchain authored-tool-validate <spec-file>` reads YAML with known-field validation, rejects `raw_script`, `run_command`, non-native runners, unknown fields, and dependency `health_command` / `install_command` arrays, and validates declared capabilities, parser, adapter id, adapter operation, inputs, expected evidence, dependency references, and safety metadata. Authored specs must choose a registered adapter operation and parser from the platform registry; `ouro toolchain authored-tool-registry` prints the allowed adapter ids, operation ids, required inputs, parser ids, and dependency names for model/tool authors. The current default registry covers managed binary operations for HTTP probing, nuclei-style template scans, path fuzzing, crawling, subdomain/DNS discovery, nmap/naabu service discovery, TLS assessment, APK decompile, static app/code scanning, secret scanning, firmware analysis, and metadata extraction. `ouro toolchain authored-tool-write <workspace> <spec-file>` persists a valid spec as:

```text
workspace/toolchain/<tool-name>/authored-tool.yaml
workspace/toolchain/<tool-name>/manifest.yaml
```

The generated `manifest.yaml` uses `runner: native`, is loadable by the existing manifest loader, and contains no command array. The authored spec remains the authoritative contract for `adapter.id` and `adapter.operation`; CLI validate/write/list/read output prints those fields for review. Tool names must be direct path-safe segments; writes refuse traversal, symlinked toolchain paths, and existing tool directories. Read/list re-derive the manifest from `authored-tool.yaml` and reject drift, so a tampered manifest cannot silently change parser, runner, commands, capabilities, or dependencies. `ouro toolchain authored-tools <workspace> [name]` lists or reads those artifacts without executing tools, probing container runtimes, or contacting targets. The registry is now consumed by tool-level compiler plans and native managed argv builders for `httpx` HTTP probing, `nmap` service fingerprinting, `nuclei` template scanning with a managed rule bundle, `naabu` CIDR port scanning, `subfinder` and `amass` explicit-domain subdomain discovery, `dnsx` and `dnsrecon` explicit-domain DNS probing, `ffuf` URL path fuzzing, `katana` URL route crawling, `dalfox` URL XSS scanning, `arjun` URL parameter discovery, `sqlmap` URL injection testing, and `mobsfscan` artifact static scanning. Most app/artifact registry operations still need argv builders, parser dispatch beyond the current narrow promoted parser set, and bundled production payloads before they should be claimed as executable coverage.

Workspace-local managed tool bundles live under:

```text
workspace/toolchain/managed-bundles/<tool>/bundle.yaml
workspace/toolchain/managed-bundles/<tool>/payload/<tool>
```

The minimal `bundle.yaml` contract is:

```yaml
name: httpx
kind: binary
version: "1.3.0"
source: projectdiscovery/httpx
payload: payload/httpx
sha256: <hex sha256 of payload/httpx>
```

`rule_bundle` payloads use the same manifest shape with `kind: rule_bundle`, `payload: payload`, and a SHA-256 digest over sorted relative file paths and file contents.

`ouro toolchain managed-bundles <workspace> [name]` lists or inspects those local bundle manifests. `ouro toolchain managed-install-plan <workspace> <pack> <dependency>` validates that the dependency exists in the selected pack manifest, resolves the matching local bundle, verifies the payload digest, and prints a metadata-only `action=link` plan. `ouro toolchain managed-install <workspace> <pack> <dependency> --execute` creates only a workspace-local link such as `workspace/toolchain/bin/httpx -> workspace/toolchain/managed-bundles/httpx/payload/httpx`; rule bundles link into `workspace/toolchain/rules/<name>`. It does not run the payload, invoke package managers, fetch remotes, contact targets, dispatch workers, or execute health probes. Payload paths must stay under the bundle directory, payloads must not be symlinks, and binary plus rule-bundle payloads require a valid SHA-256 digest.

Release archives can carry the same bundle shape under:

```text
<release-root>/toolchains/managed-bundles/<tool>/bundle.yaml
<release-root>/toolchains/managed-bundles/<tool>/payload/...
```

`scripts/release.sh` copies `toolchains/managed-bundles` into the archive when that directory exists. `scripts/install.sh` copies bundled metadata and payloads to `${PREFIX}/share/ouroboros/toolchains/managed-bundles` without writing any workspace. `ouro toolchain release-managed-install-plan <workspace> <release-root> <pack> <dependency>` validates a release bundle and prints a metadata-only `action=copy-and-link` plan. `ouro toolchain release-managed-install <workspace> <release-root> <pack> <dependency> --execute` copies the selected release bundle into `workspace/toolchain/managed-bundles/<tool>/` and then creates the same workspace-local link. It does not run the payload or link the workspace directly to the release/install directory, so workspace state survives Ouroboros upgrades or uninstall operations.

During `ouro run`, `runner: native` manifests can now consume managed binaries in process-style execution when the workspace has an installed matching binary. The runner first tries `workspace/toolchain/bin/<manifest-name>`; if that is absent and the manifest declares exactly one binary dependency, it tries that dependency name, such as `workspace/toolchain/bin/httpx`. When a managed binary is found, the native runner builds a direct argv, appends or resolves the scoped target when one exists, and delegates to the existing command runner. This preserves target-policy, exclusion, timeout, attempt-directory, and process/disabled isolation behavior; artifact path confinement under `workspace/artifacts/` remains a separate filesystem safety boundary and is not turned off by target-policy bypasses. `OURO_TOOLCHAIN_BIN` and `OURO_TOOLCHAIN_RULES` are injected into the command environment, and `workspace/toolchain/bin` is prepended to `PATH`. Container-mode native managed execution remains pending because workspace symlink targets and in-container tool availability need a separate mount-safe adapter design.

`ouro toolchain install-plan <workspace>` prints only the non-executing remediation plan rows. It is intended for operators and future TUI dispatchers that need to inspect or copy the proposed command arrays without running them.

`ouro toolchain install-request <workspace> <pack> <dependency>` writes the selected install-plan row to `workspace/toolchain/install-requests/*.json` with `status: pending`. The request is still metadata-only: it records the command array, hint, source, digest, and unresolved `depends_on` context for a later approval/execution workflow, but it does not run the command. `ouro toolchain install-requests <workspace>` prints a status summary (`total`, `pending`, `approved`, `denied`) and then lists those request artifacts without executing them. `ouro toolchain approve-install-request <workspace> <request>` and `ouro toolchain deny-install-request <workspace> <request>` update the JSON status to `approved` or `denied`; both commands only rewrite metadata and constrain the request path to the workspace install-request directory. `ouro toolchain install-dispatch-plan <workspace>` is the future dispatcher input contract: it prints approved requests as `dispatch-install` candidates only after declared prerequisite requests exist and are approved, orders ready requests with prerequisites first, skips pending/denied/missing prerequisite requests with reasons such as `dependency-not-approved: runtime-base status=pending`, and remains metadata-only. `ouro toolchain install-dispatch <workspace>` writes that dependency-aware approved dispatch view to `workspace/toolchain/install-dispatches/*.json` as a dry-run artifact with `status: dry-run` and `mode: metadata-only`; it still does not execute installer command arrays. `ouro toolchain install-dispatches <workspace>` lists those dry-run artifacts, and `ouro toolchain install-dispatches <workspace> <dispatch>` inspects one artifact by basename or workspace-confined path. `ouro toolchain execute-install-dispatch <workspace> <dispatch> --execute` is the explicit CLI execution gate: it refuses to run without `--execute`, accepts only a dry-run metadata-only dispatch artifact, revalidates every ready request as `approved`, executes only ready command arrays, carries `doctor` safety warnings into the output, and writes an audit JSON artifact under `workspace/toolchain/install-executions/`. `ouro toolchain install-executions <workspace>` lists those execution audit artifacts, and `ouro toolchain install-executions <workspace> <execution>` inspects one artifact by basename or workspace-confined path; these commands only read JSON and do not execute installers. `ouro toolchain install-retry-plan <workspace>` reads those execution audit artifacts and prints metadata-only retry candidates for failed install results while skipping completed results with reasons; it does not create a new dispatch artifact and does not execute candidate commands. `ouro toolchain install-retry-dispatch <workspace>` persists that retry-plan state to `workspace/toolchain/install-retry-dispatches/*.json` as a dry-run metadata-only artifact; it still does not run retry commands. `ouro toolchain install-retry-dispatches <workspace>` lists those retry dry-run artifacts, and `ouro toolchain install-retry-dispatches <workspace> <dispatch>` inspects one artifact by basename or workspace-confined path without executing retry commands. `ouro toolchain execute-install-retry-dispatch <workspace> <dispatch> --execute` is the explicit CLI retry execution gate: it refuses to run without `--execute`, accepts only a dry-run metadata-only retry-dispatch artifact, revalidates each ready candidate's original install request as `approved`, executes only ready retry command arrays, carries `doctor` safety warnings into output/audit metadata, and writes a retry audit JSON artifact under `workspace/toolchain/install-retry-executions/`. `ouro toolchain install-retry-executions <workspace>` lists those retry execution audit artifacts, and `ouro toolchain install-retry-executions <workspace> <execution>` inspects one artifact by basename or workspace-confined path; these commands only read JSON and do not execute retry commands. `ouro toolchain install-orchestrate <workspace>` writes a top-level orchestration audit under `workspace/toolchain/install-orchestrations/`. By default it is `dry-run` / `metadata-only`: it records approved dispatch readiness and failed-result retry readiness, but it does not create dispatch artifacts, execute installers, or create retry dispatches. With `--execute`, it creates an approved-only install dispatch, runs that dispatch through the existing explicit execution gate, writes the execution audit, and only after a failed primary execution creates a retry-dispatch artifact for operator review. It deliberately does not auto-approve requests and does not execute retry-dispatch commands. `ouro toolchain install-orchestrations <workspace> [orchestration]` lists or inspects those top-level audit artifacts without executing commands. Interactive TUI models created for a workspace use the same request path: pressing `r` on an active install remediation action writes the pending request and renders the request status/path back into Runtime Tabs. Workspace-bound TUI models also append existing request rows, the dependency-aware approved dispatch plan, execution audit artifact rows, failed-result retry-plan rows, retry-dispatch artifact rows, retry execution audit rows, install orchestration artifact rows, and dry-run dispatch artifact rows to Toolchain Health, prioritizing ready/skipped dispatch rows and execution results before request details, rendering compact `depends_on` rows for dependent requests, and showing the compact `requests:p/a/d` count in the status bar. Pressing `d` on an execution artifact or result row opens read-only Node Inspector details for the artifact path, dispatch path, command, output, status, and result counts. Pressing `d` on a retry-dispatch artifact row opens metadata-only Node Inspector details for the retry artifact path, dry-run status, mode, and ready/skipped counts; it does not execute retry commands. Pressing `d` on a retry execution artifact or result row opens read-only Node Inspector details for retry execution path, retry-dispatch path, source execution path, original dispatch path, command, output, error, status, and counts. Pressing `d` on an install orchestration artifact row opens read-only Node Inspector details for orchestration path, status, mode, ready counts, result counts, linked dispatch/execution/retry-dispatch paths, and error metadata; orchestration artifacts do not add a TUI execution shortcut. Pressing `x` on a dry-run dispatch artifact arms execution confirmation without running anything; pressing `x` again on the same armed action calls the same execution gate used by the CLI, renders execution status/path/output/error back into Runtime Tabs, and appends the new execution artifact/result rows to Toolchain Health for both completed and failed installer runs. Pressing `x` on a dry-run retry-dispatch artifact follows the same two-step confirmation pattern and calls the same retry execution gate used by the CLI; completed and failed retry executions preserve the retry audit path, command output, error text, source execution reference, appended audit rows, and selection on the new retry execution artifact.

Use `runner: command` plus `run_command` when a manifest should execute a local binary during the `tool-execution` stage:

```yaml
runner: command
run_command:
  - httpx
  - -version
run_timeout_ms: 10000
```

Run commands are direct argument arrays, not shell strings. They execute in `workspace/attempts/<run-id>/<execution-id>/`, and combined output is recorded in the tool execution event transcript.

`run_timeout_ms` is optional and measured in milliseconds. Omit it or set it to `0` to rely only on the parent run context. A timeout records a durable tool event with `execution_status: failed`, a timeout transcript, and the attempt directory, then stops the run before report projection.

Run commands can use explicit scope templates:

- `{{target}}`: the matching target value from `scope.yaml`
- `{{target_kind}}`: the matching target kind
- `{{workspace}}`: workspace root path
- `{{run_id}}`: current run id

Target matching follows capability prefixes: `web.*` uses `url`, `infra.*` uses `cidr`, and `ctf.*` uses `challenge`. A command with target templates fails before execution if no matching scoped target exists.

Command-bound tool execution for target-bearing capabilities also requires a matching scope target even when the command does not include `{{target}}`. Use `healthcheck: exec` for version probes or readiness checks that do not operate on a scoped target.

By default, command-bound target work also enforces `scope.exclusions`. Exact trimmed matches are always excluded; URL exclusions also match normalized URL subtrees, trailing-slash variants, default ports, and explicit `*` wildcard patterns after URL normalization. CIDR exclusions match contained IP addresses or child prefixes, and explicit `*` wildcard patterns can match the normalized CIDR/IP string shape. Challenge targets support the same explicit `*` string wildcard behavior. Set `scope.target_policy: disabled` only for an explicitly authorized workspace when the local scope boundary is known to be a false positive:

```yaml
scope:
  target_policy: disabled
```

This disables the command-runner target boundary checks for matching scope targets and exclusions. It does not invent missing template values; a command using `{{target}}` still needs a matching target in `scope.yaml`.

`ouro doctor <workspace>` keeps an explicitly disabled target policy as a ready workspace state, but prints a warning so authorized bypasses remain visible in operator logs.

Command worker processes receive a constrained environment: `PATH` plus explicit `OURO_*` values for workspace, run id, execution id, attempt dir, action, capability, tool, and matching target details. They do not inherit the caller's full environment.

With `scope.target_policy: enforce`, command arguments are checked before process execution for target-bearing capabilities. Literal extraction covers standalone tokens, embedded `key=value` forms such as `--url=https://other.example` or `--host=10.0.1.5`, and comma-list values such as `targets=https://app.example,https://other.example`. `web.*` arguments are scanned for `http://` and `https://` URL literals, which must stay inside the scoped target's scheme, normalized host/default-port, and path boundary. `infra.*` arguments are scanned for IP and CIDR literals, which must stay inside the scoped CIDR target. `ctf.*` arguments are scanned for explicit `challenge:<id>` and `ctf://<id>` literals, including `--challenge=challenge:<id>` and `target=ctf://<id>`, which must match the scoped challenge target. `scope.target_policy: disabled` bypasses these checks for explicitly authorized false-positive cases.

Workspace execution isolation is controlled by `scope.yaml`:

```yaml
execution:
  isolation: process
```

`process` is the default mode. It runs the command as a direct child process in the attempt directory with the constrained worker environment above.

Tool execution concurrency is also controlled from `scope.yaml`. The default is `1`, which preserves deterministic single-worker execution. Set `tool_concurrency` above `1` to run independent compiled tool plan nodes through a bounded worker pool:

```yaml
execution:
  isolation: process
  tool_concurrency: 3
```

Workspace execution can also name local worker pools by pack. These pools are a placement and audit boundary for the in-process scheduler; they do not create remote workers or cross-process leases:

```yaml
execution:
  isolation: process
  worker_pools:
    - id: web-local
      mode: local
      max_concurrency: 2
      packs:
        - web-api-pack
    - id: infra-local
      mode: local
      max_concurrency: 1
      packs:
        - infra-pack
```

Supported worker-pool modes currently include `local`. Registered workers under `runtime/workers/` may already record `local` or `remote` modes for operator visibility, but pool placement is still local scheduler metadata and does not dispatch work to a registered remote worker. If no pool matches a manifest, the request uses `worker_id: local`. `max_concurrency` is optional; when it is positive, the local admission limiter caps concurrent workers assigned to that worker id and emits `wait_reason: worker_pool_max_concurrency` for blocked workers. Tool execution requests, scheduler admission events, worker lifecycle events, final tool execution events, replay snapshots, and the TUI Agent Runtime tab all carry the selected `worker_id` so operators can see where a pack was placed.

Each compiled plan node first writes a durable scheduler admission event before any skip or worker dispatch. These events use `kind: scheduler_admission`, `admission_action`, `admission_capability`, `admission_decision`, `execution_policy`, optional `policy_reason`, `isolation`, `container_overrides`, optional `worker_id`, optional `worker_pool_max_concurrency`, optional `pack_max_concurrency`, and optional CPU/memory request and limit fields. Replay snapshots project admission decisions into the TUI Agent Runtime tab so admitted, skipped, resource-limited, worker-placed, and policy-overridden packs are auditable without inferring scheduler behavior from worker results.

Each scheduled tool worker writes a durable `worker_status: queued` tool event before dispatch. If scheduler admission cannot immediately acquire global, worker-pool, pack, CPU, or memory capacity, the worker writes a durable `worker_status: waiting` event with `wait_reason` such as `global_concurrency`, `worker_pool_max_concurrency`, `pack_max_concurrency`, `cpu_units`, or `memory_mb`. A `worker_status: started` event is written when execution actually begins, followed by a final `execution_status: completed` or `failed` event. Replay snapshots project these worker states into the TUI Agent Runtime tab so queued, waiting, active, completed, and failed workers are visible during live or replayed runs.

Scheduler admission can also disable specific packs before worker dispatch. A disabled pack writes a durable admission decision and a durable `execution_status: skipped` tool event with the policy reason, but it does not emit queued/started worker events and does not call the runner:

```yaml
execution:
  isolation: process
  tool_concurrency: 3
  resource_limits:
    cpu_units: 2
    memory_mb: 1024
  pack_policies:
    - pack: web-api-pack
      mode: disabled
      reason: noisy active scan deferred for this run
    - pack: infra-pack
      mode: enabled
      reason: serialize heavier discovery workers
      max_concurrency: 1
      cpu_units: 1
      memory_mb: 512
```

Supported pack policy modes are `enabled` and `disabled`. Policy entries must reference workspace-local toolchain manifest names. `max_concurrency` is optional and limits concurrent workers for that pack when global `tool_concurrency` is higher; omit it or set it to `0` for no pack-specific limit. `resource_limits.cpu_units` and `resource_limits.memory_mb` define local scheduler lease pools, and pack-level `cpu_units` / `memory_mb` request leases from those pools before a worker starts. The local scheduler admits global, pack, and CPU/memory capacity atomically, so waiting requests do not reserve partial capacity and compatible workers can still start. These leases are in-process admission controls for scheduling fairness and audit visibility; container/cgroup resource enforcement remains controlled separately by `execution.container` fields.

`container` runs command-bound tools through a container engine. `execution.container.image` is required and `execution.container.engine` defaults to `docker` when omitted. The workspace is mounted at `/workspace`, the container workdir is `/workspace/attempts/<run-id>/<execution-id>`, and `OURO_*` values are injected with container paths. The host only resolves the container engine; the inner `run_command` binary is resolved inside the container image:

```yaml
execution:
  isolation: container
  container:
    engine: docker
    image: ouro-worker:latest
    network: bridge
    read_only_rootfs: true
    no_new_privileges: true
    cap_drop:
      - ALL
    memory: 512m
    cpus: "1.5"
    pids_limit: 128
    seccomp: default
    apparmor: ouro-default
    tmpfs:
      - /tmp:rw,nosuid,nodev,noexec,size=64m
```

Pack policies can override selected container settings for admitted packs while inheriting unspecified global values. This lets a workspace use one engine and default sandbox profile while pinning a different worker image or resource profile for a specific pack:

```yaml
execution:
  isolation: container
  container:
    engine: docker
    image: default-worker:latest
    network: bridge
  pack_policies:
    - pack: web-api-pack
      mode: enabled
      container:
        image: web-worker:latest
        network: none
        memory: 256m
        cpus: "0.5"
```

String, slice, pointer, and positive numeric container fields override the global value when present. Boolean `read_only_rootfs` currently only overrides in the stricter direction when set to `true`; relaxing a global `true` value remains a later policy-normalization task.

Container sandbox defaults are intentionally constrained: `network` defaults to `bridge`, `no_new_privileges` defaults to `true`, and omitted `cap_drop` defaults to `ALL`. Authorized compatibility cases can explicitly relax those settings with `no_new_privileges: false`, `cap_drop: []`, `network: host`, or by omitting optional resource/profile controls.

`ouro doctor <workspace>` preflights container mode by resolving the configured engine and running `image inspect <image>`. A missing engine or unavailable image marks the workspace unready before a run starts.

`disabled` is available for explicitly authorized legacy-tool compatibility; it runs from the workspace root and inherits the host environment while still appending `OURO_*` context and durable replay events:

```yaml
execution:
  isolation: disabled
```

`ouro doctor <workspace>` also warns when execution isolation is disabled, because this mode intentionally gives up the constrained worker environment.

Workspaces created by `ouro init` include an `authorization.yaml` template. When `scope.target_policy: disabled` or `execution.isolation: disabled` is configured, add a matching `safety_bypasses` entry so the bypass has an auditable approver, reason, ticket, and optional expiry:

```yaml
version: 1
safety_bypasses:
  - control: scope.target_policy
    mode: disabled
    authorized_by: security-lead
    reason: authorized false-positive boundary in client lab
    ticket: ENG-123
    expires: "2026-06-30"
  - control: execution.isolation
    mode: disabled
    authorized_by: security-lead
    reason: legacy tool requires host environment
    ticket: ENG-124
```

`ouro doctor <workspace>` validates `authorization.yaml` when it exists. By default, a disabled safety boundary without a matching authorization remains ready but prints a missing-authorization warning; malformed authorization metadata makes the workspace unready. Optional `expires` values accept `YYYY-MM-DD` dates or RFC3339 timestamps. Invalid expiry text makes `authorization.yaml` invalid, and expired authorization is retained for audit visibility but no longer counts as current authorization. For production or CI gates, `ouro doctor <workspace> --require-safety-authorization` keeps the same visible warnings but marks the workspace unready when `scope.target_policy: disabled` or `execution.isolation: disabled` lacks a matching current, unexpired `authorization.yaml` entry. CI runs this through `make doctor-strict`, while `make doctor` remains warning-only for authorized false-positive testing workflows.

`ouro run <workspace>` also records safety state as a durable replay event. The first event in each run is `verification` with `kind=workspace_safety`, carrying `target_policy`, `isolation`, warnings, structured `safety_bypasses`, and a gate summary. Default runs keep disabled safety boundaries warning-only and auditable. `ouro run <workspace> --require-safety-authorization` turns the run gate strict: missing or expired safety-bypass authorization writes one blocked `workspace_safety` audit event and then fails before provider preparation, tool execution, report projection, endpoint contact, or target contact. When a strict run proceeds, started tool-worker lease acquisition and completion also recheck current authorization before writing or rewriting `workspace/runtime/worker-leases/<run-id>/<execution-id>.json`; if authorization is removed or expires after startup, the run fails before those lease mutations. For `scope.target_policy`, the bypass also disables the embedded run-command argument literal checks described above. Restoring `scope.target_policy: enforce` and `execution.isolation: process` or `container` is still the close/off path for the bypass.

The runtime-worker queue-dispatch, worker-side HTTP receive/artifact ingress, daemon-control creation, file-outbox ack, request-command execution, worker queue dispatch result submission, retry-dispatch execution, active-lease heartbeat, active-lease release, stale-lease reclaim execution, lease/result reconciliation execution, and opt-in daemon-control consumption gates reuse the same current safety authorization semantics. Disabled target-policy or isolation settings without matching unexpired bypass metadata fail those gates before queue dispatch mutation or contact, accepted HTTP receive file-outbox artifact writes, pending daemon-control request creation, acknowledgement, request-command execution, result submission, retry-claim creation, lease heartbeat writes, lease release writes, reclaim writes/execution audits, reconciliation release writes/execution audits, or pending stop/restart daemon-control consumption and applied-status audit writes, while read-only and metadata-only review paths stay available. Worker-side HTTP receive still validates bearer token, worker id, and transport mode before the safety preflight, so missing or wrong bearer tokens return `401` responses without safety details. Daemon-control creation validates worker id/action before safety preflight and writes pending control artifacts only with current authorization under disabled boundaries. Ordinary run lease acquire/complete writes are not counted as runtime-worker direct gates, but strict `ouro run --require-safety-authorization` rechecks current authorization before those lease writes; daemon-control list/read remain outside the direct gate list.

Workspace-bound TUI models also render these safety-bypass warnings in Toolchain Health as `workspace safety` rows. They include a read-only `workspace safety strict gate` status: `ready` when all configured bypasses have matching current authorization metadata, and `blocked` with strict error rows when `make doctor-strict` / `ouro doctor --require-safety-authorization` would fail because authorization is missing or expired. Selecting the strict gate row, individual `safety warning:` rows, or `safety error:` rows and pressing `d` opens Node Inspector details for status, mode, and reason. Pressing `x` on workspace safety rows is unsupported and does not call an executor. Malformed authorization metadata is surfaced as an inspectable `safety error:` row before toolchain install-request listing can hide it. When the workspace is restored to `scope.target_policy: enforce` and `execution.isolation: process` or `container`, these bypass rows disappear. This keeps disabled target-boundary or isolation modes visible during interactive work without running full `doctor` preflights from the TUI safety projection.
