# Ouroboros

Ouroboros is a TUI-first penetration testing IDE and compiler for authorized security work. It turns scoped objectives into auditable plans, toolchain actions, runtime worker state, replayable evidence, and operator-controlled execution gates.

## Current Shape

- Goal-driven architecture with domain packs for Web/API, Infra/Internal, and CTF/Lab work.
- Native Go CLI under `cmd/ouro/` with first-party packages under `internal/`.
- Bubble Tea TUI surfaces toolchain health, agent runtime, replay timelines, evidence graph state, and read-only inspector details.
- `ouro chat <workspace>` launches the workspace-bound AI chat IDE directly with the Mission Conversation composer already focused, so operators do not have to start a run or remember the `i` shortcut before talking to the configured provider. `ouro chat <workspace> --tui` prints the same focused first-screen snapshot for smoke logs and non-interactive checks. The active terminal composer renders as `You > <draft>|`, so typed prompts are visually separate from assistant output before submission. After provider replies, local command responses, provider errors, and `/clear`, the dialog reopens an empty `You > |` composer so the next prompt can be typed immediately. Fresh workspaces now show an `AI setup:` row in Mission Conversation and Model Runtime with the `ouro provider configure-openai-compatible ... --api-key-env <ENV_VAR> --capability chat --capability tool_planning --enable` command hint; if a prompt is submitted while the default `offline` provider is still active, the dialog error repeats the same setup command instead of leaving the operator to infer the next step. `ouro run --interactive` and `ouro replay --interactive` still expose the same composer through `i`. The local `/quickstart`, `/use`, and `/runbook` commands return path-safe first-use commands (`./bin/ouro init <workspace>`, `./bin/ouro chat <workspace>`), a provider configuration skeleton with `<base-url>`, `<model>`, `<ENV_VAR>`, `api_key_value_stored=false`, `make smoke-ide`, and a compact local-command pointer without provider calls or artifact writes. The local `/keys`, `/shortcuts`, and `/controls` commands return a provider-free TUI key map for chat focus, submit, draft cancel, quit, runtime row selection, details, double-confirm execution, metadata requests, replay stepping, and run pause/cancel controls without provider calls or artifact writes. The local `/doctor`, `/readiness`, and `/health` commands return provider-free workspace readiness across metadata-only doctor, strict safety, provider setup, workflow gate, and toolchain contract status without provider calls or artifact writes. The local `/completion`, `/progress`, `/percent`, `/acceptance`, and `/completion-status` commands return a provider-free completion posture with `local_ide_usable=true`, direct-chat availability, `completion_estimate=99.99`, `claim_100_ready=false`, and the remaining external evidence/attestation/manifest/operator-acceptance gates without provider calls, path disclosure, or artifact writes. The local `/status`, `/workflow`, and `/workflow-status` commands return the current workflow status and next gate inside the conversation without calling a provider; `/next` and `/next-gate` return a compact next-gate/action summary with `command_available` metadata while omitting command strings and paths; `/command`, `/next-command`, and `/workflow-command` return a sanitized next command template with the workspace root replaced by `<workspace>`; `/artifacts`, `/artifact-counts`, and `/workflow-artifacts` return the current workflow artifact counts; `/gates`, `/review-gates`, and `/gate-status` return a count/status-only review-gate posture across preview acceptance, compile dispatch/execution, report projection, safety errors, and current command availability without exposing paths or commands; `/runs`, `/replay-runs`, and `/run-history` return the replay run count and latest run id through a read-only SQLite open; `/evidence`, `/findings`, and `/graph` return latest-run evidence graph, finding, surface, artifact, path, evidence-ref, exhausted-area, and suggestion counts through the same read-only replay path without exposing run ids, fact ids, statements, URLs, hosts, artifact paths, or report text; `/mission`, `/targets`, and `/target-scope` return mission/scope readiness, goal presence, target policy, isolation mode, target-kind counts, and exclusion counts without exposing mission names, goal text, target values, exclusion values, workspace paths, provider setup commands, or secrets; `/reports`, `/report-status`, and `/current-report` return report projection dispatch/execution counts plus current-report metadata without exposing report paths; `/toolchain`, `/tools`, and `/toolchain-contract` return toolchain contract status/counts without running tools or exposing manifest paths; `/capabilities`, `/packs`, and `/domains` return count-only domain-pack, semantic-action, manifest, tool catalog, managed-bundle, parser, strategy, category, and target-kind coverage without listing tool names, command arrays, manifests, payload paths, or install paths; `/overview`, `/summary`, and `/dashboard` return one count/status-only posture line across workflow, mission, safety, providers, capabilities, evidence, reports, and workers without exposing targets, provider metadata, paths, commands, or secrets; `/safety`, `/scope`, and `/authorization` return read-only safety readiness, strict-readiness, warning/error, and safety-bypass counts without exposing scope or authorization file paths; `/context` returns the same compact read-only workspace context that normal provider prompts receive, including safe semantic-action marker guidance, without provider setup or artifact writes; `/actions`, `/semantic-actions`, and `/action-list` return the declared semantic-action IDs plus `semantic_action:<action>` preview marker format without provider setup, tool names, command arrays, manifest paths, or artifact writes; `/usage` returns the metadata-only provider usage summary already recorded by explicit preview paths, without calling a provider or writing usage records; `/providers`, `/provider`, and `/models` return a safe provider configuration summary with setup status, counts, routing, first-provider type/model, capability booleans, and API-key environment presence without exposing provider URLs, environment variable names, or API key values; `/workers`, `/agents`, and `/runtime` return a safe worker runtime summary with registration, queue, transport, dispatch-result, and lease counts without exposing worker IDs, endpoints, labels, commands, artifact paths, or secrets; `/setup` returns the current provider setup state and configure command; `/clear` clears the current in-session transcript and provider history; and `/help` lists the local commands plus the provider-backed prompt boundary, so a fresh offline workspace still has useful interaction and discoverability. Local command prompts and responses are marked out of provider history, so later normal prompts do not send `/quickstart`, quickstart runbook text, `/keys`, keymap text, `/doctor`, readiness text, `/completion`, completion posture text, `/overview`, `/context`, `/actions`, `/usage`, `/providers`, `/workers`, `/evidence`, `/mission`, `/next`, `/command`, `/artifacts`, `/gates`, `/runs`, `/reports`, `/toolchain`, `/capabilities`, `/safety`, `/setup` output, workspace paths, provider summaries, worker runtime summaries, evidence summaries, mission/scope summaries, capability summaries, semantic-action summaries, overview summaries, review-gate summaries, or configure-command text to the model. Normal prompts inject an Ouroboros security-IDE system prompt with compact read-only workflow context, safe semantic-action marker guidance, and count/status-only overview context, then send current-session non-local chat history to the provider as ordered user/assistant messages before the new user prompt, so follow-up questions have context and current next-gate awareness. The context includes safe workflow state such as status, stage, next gate, reason, action, counts, and safety-error count; declared semantic-action IDs, count, `semantic_action:<action>` marker format, preview-only mode, and operator-review requirement; plus overview fields for mission configuration, target-policy mode, target count, safety/provider/capability/evidence/report/worker posture. It deliberately omits workspace paths, command strings, tool names, command arrays, manifest paths, target values, provider URLs, model names, API-key environment names, prompt text, full assistant text, and API key values. The response is displayed in the current TUI session with provider/model/token metadata, and the dialog keeps `stored=false` by default: prompt text, full assistant text, and multi-turn history are not written to replay, reports, or the provider usage ledger by this interactive chat path. When the response contains exactly one valid declared action marker such as `semantic_action: enumerate_paths` or `ouro_action: enumerate_paths`, the workspace-bound TUI creates an existing metadata-only model tool-plan preview artifact plus a linked compile-preview review and refreshes Model Runtime rows so the operator can accept it through the existing double-confirm `x` gate. Model suggestions still do not execute tools or commands; execution remains behind the existing operator-reviewed gates.
- `/final`, `/final-evidence`, `/final-review`, `/audit`, `/audit-completion`, and `/production-acceptance` are local AI-dialog commands for the final evidence runbook. They return only the production acceptance, payload-inventory, deployment-policy, completion-attestation, completion-audit, manifest/digest-sidecar, and operator-acceptance gates with placeholders and `stored=false`; they do not call providers, write artifacts, execute tools, contact targets, expose paths or secrets, or claim 100%.
- Provider configuration supports the default `offline` runtime plus an `openai_compatible` readiness preflight that checks `GET <base_url>/models/<model>` with an optional bearer key read only from an environment variable. `ouro provider configure-openai-compatible` writes the provider entry from CLI flags, stores only the environment variable name, moves the configured provider first, and disables the default offline provider when the real provider is enabled. It also exposes a manual `ouro provider generate` preview that calls `POST <base_url>/chat/completions` and prints assistant text, token usage, optional context/capability metadata, optional cost estimates, explicit failover routing metadata, optional required-capability routing metadata, and explicit `--stream` metadata; `--max-estimated-cost-usd` adds an explicit preview budget gate, and `--record-usage` writes a metadata-only usage ledger record that can be listed, inspected, summarized with `ouro provider usage`, and previewed read-only in the workspace TUI Model Runtime tab and hosted replay workbench. Default `ouro run` remains offline-compatible and does not use provider generation for automated attack flow; `ouro run --provider-generate` plus the related `--provider-generate-*` flags are the explicit opt-in boundary for one run-integrated planner generation call, which now also writes a metadata-only review artifact inspectable with `ouro provider generations` and can request safe streamed output metadata through `--provider-generate-stream`.
- `ouro run --provider-generate --provider-generate-tool-plan-preview` can additionally parse a single safe marker line from the bounded provider output, such as `ouro_action: enumerate_paths` or `semantic_action: enumerate_paths`, and turn a declared semantic action into a metadata-only tool-plan preview review. The interactive TUI AI dialog can create the same preview artifact type from a valid response marker, with `source=tui-ai-dialog`, without replay/model-generation artifact writes. The resulting `model_tool_plan_preview` replay event when created by run-integrated generation, and the shared `workspace/runtime/model-tool-plan-previews/` artifacts for both paths, are inspectable with `ouro provider tool-plan-previews` and workspace-bound Model Runtime rows. A separate explicit `ouro provider tool-plan-preview-accept ... --accept` gate accepts only valid completed metadata-only preview artifacts, writes `workspace/runtime/model-tool-plan-preview-acceptances/`, and selects the linked compile-preview review as current. The preview and acceptance paths store marker/digest/action/review/acceptance metadata only and do not persist the prompt, full assistant text, raw provider bodies, bearer tokens, executable model instructions, tool execution, worker dispatch, another tool round, provider calls, or scoped target contact.
- AI-dialog-created preview notifications in Mission Conversation show only status, action, marker, `artifact_created=true|false`, and `stored=false`. Artifact paths remain in Model Runtime rows and Inspector details, not in the chat transcript.
- `/previews`, `/tool-plan-previews`, and `/model-previews` are local AI-dialog commands for a path-free model-preview posture summary. They report preview, valid, completed, acceptance, pending-acceptance, latest-action/status, latest-valid, and review-available fields with `stored=false`, without provider setup, provider calls, artifact path disclosure, provider/model disclosure, replay mutation, model/usage artifact writes, execution dispatch, worker dispatch, tool execution, or target contact.
- `/gates`, `/review-gates`, and `/gate-status` are local AI-dialog commands for a path-free review-gate posture summary. They report workflow status/stage/next gate/reason/action, preview and acceptance counts, compile dispatch/execution counts, report dispatch/execution counts, whether a current report is selected, safety-error count, and `command_available`, without provider setup, provider calls, artifact path disclosure, command disclosure, provider/model disclosure, replay mutation, artifact writes, execution dispatch, worker dispatch, tool execution, or target contact.
- `ouro workflow-status <workspace>` projects the next operator gate across model tool-plan preview, preview acceptance, compile-preview dispatch/execution, and report projection dispatch/execution/selection state. When the next gate would be blocked by missing or expired strict safety-bypass authorization, it returns `next_gate=safety-authorization` with strict doctor guidance instead of failing or suggesting an unusable accept/execute command. It prints `next_gate`, a command hint, counts, safety error count, and artifact links; workspace-bound Model Runtime renders matching `workflow status:` and `workflow status links:` rows with Inspector details. The CLI status path is read-only. The workspace-bound TUI may promote only four narrow report-projection workflow states into double-confirm `x` actions: create report dispatch, execute report dispatch, review report execution, and select the accepted report execution. These shortcuts reuse the existing app gates and keep all other workflow-status rows read-only.
- `make smoke-ide` is the local "can I use the IDE now?" smoke. It uses the built `bin/ouro` by default and runs both `smoke-direct-use` and `smoke-ai-provider` in separate fresh sub-workspaces, proving the core built-binary TUI/replay/workflow-status path and the direct AI provider/manual usage path together. It writes stage logs under one smoke log directory, refuses existing non-empty workspace roots unless `OURO_IDE_SMOKE_ALLOW_EXISTING_WORKSPACE=1` is set for a known-safe smoke root, and does not contact real providers, endpoints, or targets.
- `make smoke-workflow` runs a local core IDE smoke over `ouro init`, strict `doctor`, `run --tui`, `replay --tui`, and `workflow-status`, printing a compact summary and writing raw outputs to a smoke log directory. It creates a fresh temporary workspace by default; a provided existing non-empty `WORKSPACE` is refused unless `OURO_SMOKE_ALLOW_EXISTING_WORKSPACE=1` is explicitly set for a known-safe smoke workspace.
- `make smoke-direct-use` verifies the currently built `bin/ouro` binary directly, without `go run`: it initializes a fresh workspace, runs `doctor`, confirms the `chat <workspace>` IDE entrypoint is present, prints `chat <workspace> --tui` and requires the focused `You > |` composer, executes `run --tui`, replays the run with `replay --tui`, checks `workflow-status`, and verifies the generated report plus compile-preview review/selection artifacts. It creates a fresh temporary workspace by default; a provided existing non-empty `WORKSPACE` is refused unless `OURO_DIRECT_USE_SMOKE_ALLOW_EXISTING_WORKSPACE=1` is explicitly set for a known-safe smoke workspace. `OURO_DIRECT_USE_SMOKE_BIN` can point at an absolute alternate built binary for installed-binary checks. Provided direct-use binary, workspace, and log-directory paths must be absolute, must not be symlink leaves, and must not pass through existing symlink path components.
- `make smoke-ai-provider` verifies the direct AI provider path against a local fake OpenAI-compatible server: it initializes a fresh workspace, configures `openai_compatible` through `provider configure-openai-compatible`, confirms strict workspace readiness, calls `provider generate --record-usage`, submits one non-interactive `chat <workspace> --prompt ...` through the same AI dialog path, verifies that the prompt creates exactly one metadata-only tool-plan preview without creating `replay/events.db`, verifies the metadata-only usage summary, and checks that the smoke API key value is not printed or written to `providers.yaml`, chat output, or usage records. It creates a fresh temporary workspace by default and refuses existing non-empty workspaces unless `OURO_AI_PROVIDER_SMOKE_ALLOW_EXISTING_WORKSPACE=1` is set for a known-safe smoke workspace. The fake provider listens only on `127.0.0.1`; the smoke does not contact real providers, endpoints, or targets.
- `make smoke-workflow-closure` runs the deferred workflow closure smoke over `ouro init`, strict `doctor`, `run --defer-report-projection`, `workflow-status`, compile-preview dispatch creation/execution, report-projection dispatch creation/execution, accepted report review, current report selection, and closed-run `replay --tui`. It creates a fresh temporary workspace by default and refuses an existing non-empty `WORKSPACE` unless `OURO_WORKFLOW_CLOSURE_SMOKE_ALLOW_EXISTING_WORKSPACE=1` is explicitly set for a known-safe smoke workspace. Provided `WORKSPACE` and `OURO_WORKFLOW_CLOSURE_SMOKE_LOG_DIR` paths must be absolute and must not be symlinks. Compile dispatch creation uses the exact `workflow-links review=` artifact from the just-read workflow status rather than guessing a review by directory contents. The script follows explicit operator gates and does not execute `workflow-command` hints, call providers, download payloads, run package managers, or contact endpoints/targets beyond the existing offline reviewed node execution path.
- `make smoke-release-managed` runs a local release-managed acceptance smoke over a newly built release archive, checksum-verifying install, installed `${PREFIX}/bin/ouro`, strict doctor, release-managed inventory/status with a matched expected digest pin, status-source marker readback, metadata-only install planning, rejection of `release-managed-install` without `--execute`, `release-managed-install --execute` for `nuclei-templates`, post-install linked status, and `run --tui`. It uses fresh temporary `DIST_DIR`, `PREFIX`, `WORKSPACE`, and log directories by default; a provided existing non-empty `WORKSPACE` is refused unless `OURO_RELEASE_MANAGED_SMOKE_ALLOW_EXISTING_WORKSPACE=1` is explicitly set for a known-safe smoke workspace.
- `make smoke-managed-payloads` runs an offline operator-supplied payload acceptance smoke for a local managed binary and rule bundle. Operators provide absolute, non-symlink local payload paths and expected SHA-256 pins through `OURO_MANAGED_BINARY_PAYLOAD`, `OURO_MANAGED_BINARY_EXPECTED_SHA256`, `OURO_MANAGED_RULE_BUNDLE_PAYLOAD`, and `OURO_MANAGED_RULE_BUNDLE_EXPECTED_SHA256`; provided `WORKSPACE` and `OURO_MANAGED_PAYLOADS_SMOKE_LOG_DIR` paths must also be absolute and must not be symlinks. The script imports, plans, rejects missing `--execute`, links, and reads back both bundles in a fresh workspace without downloading, running payloads, calling package managers, contacting providers/workers/endpoints/targets, or mutating replay/report state.
- The non-production smoke entrypoints above start through `/bin/sh` and reset `PATH` to a trusted system path before `ROOT` resolution, temporary directory creation, workspace/log preflight, `go run`, release build/install calls, or CLI smoke commands. Regression tests prove caller-controlled `PATH/sh`, prelude `dirname`, and fake `go` do not steer direct execution.
- `make smoke-production-acceptance` runs the top-level production acceptance audit harness. It requires an operator-owned payload inventory file through `OURO_PRODUCTION_ACCEPTANCE_INVENTORY` and an approved deployment policy file through `OURO_PRODUCTION_ACCEPTANCE_POLICY`; both are read as fixed `key=value` fields with one occurrence per key and are not sourced as shell. The audit validates required fields, expected SHA-256 pins, safe policy booleans, and absolute non-symlink local payload paths whose existing path components are also non-symlinks, then runs local IDE usability, release-managed acceptance, operator managed-payload acceptance, and workflow-closure acceptance in separate fresh sub-workspaces through a trusted system shell and trusted `PATH`. The IDE stage builds a workspace-confined `ouro` binary and runs `smoke_ide.sh`, including the local fake-provider AI path. It writes raw logs plus `summary.txt` with inventory/policy SHA-256s, trusted shell/path, stage script SHA-256s, IDE child script SHA-256s, stage workspace paths, log paths, IDE child log paths, log SHA-256s, `no_live_targets=true`, and accepted/failed status. Provided `WORKSPACE`, inventory, policy, and payload paths must be absolute, must not be symlinks, and must not pass through existing symlink path components; an existing non-empty `WORKSPACE` is refused unless `OURO_PRODUCTION_ACCEPTANCE_SMOKE_ALLOW_EXISTING_WORKSPACE=1`. The harness does not download payloads, run package managers, execute managed payloads, call real providers/workers, or contact live endpoints/targets.
- `make smoke-final-evidence-fixture` runs a local fixture-only final evidence chain. It creates a temporary operator-style binary payload, uses the bundled release-managed `nuclei-templates` payload and manifest SHA-256, writes fixed inventory/policy evidence, runs production acceptance, creates an attestation bound to the generated `summary.txt`, runs completion audit, prints `completion-status`, and verifies `completion-accept` rejects the fixture evidence. It is a regression smoke for the full evidence mechanics and always reports `claim_100_ready=false`; `completion-status` also surfaces `final_review_status=fixture_evidence_not_acceptable` and `fixture_evidence_detected=true` for this chain so fixture evidence is not confused with operator-acceptable final evidence. It does not replace real operator-owned payload evidence, approved attestation review, manifest/digest sidecar review, or final human/operator acceptance.
- `make audit-completion` runs the final completion evidence gate. It requires a production acceptance `summary.txt` through `OURO_COMPLETION_AUDIT_PRODUCTION_SUMMARY` and a separate approved operator attestation through `OURO_COMPLETION_AUDIT_ATTESTATION`; the summary, attestation, and referenced inventory/policy evidence are fixed `key=value` files with one occurrence per key. The audit verifies the production acceptance status, stage log files and matching SHA-256s, IDE child smoke script/log digests including `chat: available` and `chat: composer` in the direct-use child log, full inventory/policy evidence shape including `inventory_sha256`, `policy_sha256`, and absolute non-symlink payload paths, safe boundary flags including `no_live_targets=true`, and attestation fields such as `production_summary_sha256`, `production_evidence=operator_owned`, and `fixture_evidence_allowed=false`, then writes `completion-audit.txt` with `status=ready-for-final-review`, `completion-evidence-manifest.txt` with the reviewed result/evidence paths/artifact digests, and `completion-evidence-manifest.sha256` with `result_sha256` plus `evidence_manifest_sha256` for final operator review. Successful result, manifest, and digest-sidecar evidence also bind the audit runner itself through `completion_audit_trusted_shell`, `completion_audit_trusted_path`, `completion_audit_script`, and `completion_audit_script_sha256`. It does not run tools, sign evidence, provide append-only storage, or claim 100% by itself; it preserves the final human/operator review step before marking the IDE target complete.
- `ouro completion-status <audit-log-dir>` is a read-only final-review status check for the three completion-audit evidence files plus the optional final operator acceptance artifact. The audit log directory, evidence paths, and final-acceptance linked paths must be canonical absolute paths, must not contain `.` or `..` spellings, must not be symlink leaves, and must not pass through existing symlink path components. Before final acceptance, it verifies the completion result, manifest, and digest sidecar are schema/link/manual-step/digest matched and keeps `claim_100_ready=false`. When the otherwise-ready evidence is fixture-marked, it reports `final_review_status=fixture_evidence_not_acceptable`, `fixture_evidence_detected=true`, and `remaining_manual_step=replace_fixture_evidence_with_real_operator_evidence` instead of `operator_review_required`. After explicit real-evidence acceptance, it also verifies `completion-final-acceptance.txt` is schema-valid, path-bound, digest-bound to the current result/manifest/digest sidecar plus manifest-linked production summary, attestation, and policy files, and not fixture-marked before reporting `claim_100_ready=true`.
- `ouro completion-accept <audit-log-dir> --reviewed-by <operator> --accept-real-evidence [--accepted-at <RFC3339>]` writes `completion-final-acceptance.txt` only after `completion-status` would otherwise be `ready-for-final-review`. The audit log directory, linked evidence files, and final acceptance output path must be canonical absolute paths, must not contain `.` or `..` spellings, must not be symlink leaves, and must not pass through existing symlink path components. The artifact records final operator identity/time, fixed paths and SHA-256s for result, manifest, digest sidecar, production summary, completion attestation, and deployment policy, `real_operator_evidence_reviewed=true`, `fixture_evidence_accepted=false`, and `claim_100_ready=true`. Fixture evidence is rejected by policy/attestation markers such as `deployment_environment=fixture`, `authorization_scope=fixture-only...`, or `final-evidence-fixture` reviewer metadata; this command is a local mutable acceptance record, not a signature or append-only ledger.
- Local release builds write `SHA256SUMS`; `scripts/install.sh` verifies the matching checksum entry when that file is present beside the archive before extracting or installing.
- Local release builds include a minimal managed `nuclei-templates` rule bundle seed with a verified payload digest plus recorded manifest provenance, offline update metadata, and an offline rule-corpus index, so operators can inspect release/workspace import status, currentness, and corpus acceptance metadata first and then explicitly import the rule directory into a workspace without network access. This is a packaging/provenance/currentness/corpus-index seed, not the full upstream Nuclei template corpus.
- Built-in toolchain manifests now expose optional managed dependency metadata for common Web/API, Infra/Internal, and artifact/app analysis tools such as `nuclei`, `httpx`, `subfinder`, `ffuf`, `katana`, `gau`, `waybackurls`, `dalfox`, `arjun`, `nmap`, `naabu`, `dnsx`, `apktool`, `jadx`, and `mobsfscan`.
- `ouro toolchain contract-check <workspace>` provides a read-only compiler/domain/manifest/strategy/parser contract check. It verifies that semantic actions map to provided capabilities, domain pack capabilities are reachable through their declared actions, built-in strategy pattern contract names resolve, catalog tools stay inside their declared pack capabilities/dependencies, workspace manifest parser ids are registered, catalog parser ids are registered, catalog parser ids are supported by their declared adapter operation, and manifest-level capabilities such as `ctf.result_proof` are not hidden by same-pack tool-level candidates. The command uses a metadata-only workspace readiness preflight, reads workspace manifests plus static built-in contracts, and does not run tools, dependency health probes, or container runtime probes. Workspace-bound TUI Toolchain Health now surfaces the same contract status as compact read-only `toolchain contract:` rows with Inspector details; blocked contracts show the total error count plus a small sample of error rows and keep full output in the CLI command.
- Default `ouro run` records a metadata-only closed-loop planner preview after the first tool-execution stage and before report projection. The preview replays current run state, asks the Sisyphus engine for the next task, reads the selected intent's semantic action, creates a dry-run tool compile preview review plus current selection marker under `workspace/toolchain/`, and persists planner agent, planner review, hint, and `kind=suggestion` fact events so replay, the TUI Attack Graph, workspace-bound TUI Toolchain Health, and Markdown reports show the operator-review next plan. Operators can execute the selected review directly through an explicit CLI/app gate, or persist a separate dry-run execution dispatch artifact and execute that dispatch with `--execute`; both execution paths reuse strict safety authorization and frozen review nodes. Workspace-bound TUI Toolchain Health can create the same dry-run dispatch from the current review and execute that dispatch only through double-confirm `x`, while non-dry-run dispatch artifacts and execution audit rows remain read-only.
- Model-authored tools must be structured native specs with declared adapter/operation, inputs, expected evidence, parser, dependency references, and safety controls; raw scripts, command-runner payloads, unknown YAML fields, and dependency command arrays are rejected before workspace artifacts are written.
- Workspace-local and release-packaged managed tool bundle metadata can be discovered, planned, copied, and linked into `workspace/toolchain/bin/` or `workspace/toolchain/rules/` through explicit metadata-first commands; release archives now seed the managed `nuclei-templates` rule-bundle path, while a broader real third-party binary payload corpus remains a separate follow-up. Bundle manifests may include an optional `provenance:` block with `source_url`, `upstream_version`, `retrieved_at`, and `verified_by`; CLI and TUI rows expose `provenance_status=missing|recorded|blocked` plus the recorded values, and invalid provenance metadata blocks read/status before workspace writes. Manifests may also include an optional offline `update:` block with `latest_version`, `latest_sha256`, `checked_at`, and `message`; CLI and TUI rows expose `update_status=unknown|current|update_available|blocked` plus the recorded values, and invalid update metadata blocks read/status before workspace writes. `rule_bundle` manifests may also include an optional offline `corpus:` block with `schema`, `name`, `source`, `retrieved_at`, `file_count`, `digest_algorithm`, `digest_scope`, and `sha256`; CLI and TUI rows expose `corpus_status=missing|recorded|blocked`, `corpus_digest_status=missing|matched|blocked`, and the recorded corpus fields. Present corpus metadata is validated against the actual rule directory file count and canonical directory SHA-256, and invalid present corpus metadata blocks read/status before workspace writes; missing corpus metadata remains a visible `missing` state. Provenance and update metadata are offline review clues, not trust roots, downloaders, sync policies, expected pins, status-source policies, or workspace conflict criteria. Corpus metadata is an offline acceptance index for rule bundles, not a downloader, sync policy, trust root, expected pin, status-source policy, workspace conflict criterion, or full upstream corpus claim. `ouro toolchain managed-bundle-import <workspace> <name> <payload> --kind binary|rule_bundle --version <version> --source <source> [--expected-sha256 <sha256>] --import` imports operator-supplied local payloads without executing them: `binary` copies a regular file into `workspace/toolchain/managed-bundles/<name>/payload/<name>`, while `rule_bundle` copies a non-empty directory into `workspace/toolchain/managed-bundles/<name>/payload/` with canonical record v1 directory SHA-256 over sorted slash-normalized relative paths, path lengths, file sizes, and per-file content SHA-256 values, and copied rule files normalized to `0644`. Source files are opened only after the prior `Lstat` is revalidated with `file.Stat()` / `os.SameFile`, so a source path replaced by a symlink or different inode after inspection is rejected before digest/copy success. Expected digest validation happens before any workspace bundle write, accepted expected digests are normalized to lowercase, and the command stops before final install links. ## Safety Boundary

Use this project only for systems where authorization and scope are documented.

The workspace keeps two explicit escape hatches for false-positive or legacy-tool cases:

- `scope.target_policy: disabled`
- `execution.isolation: disabled`

Safety isolation and target-boundary checks must have an explicit closeable/off path so authorized false-positive boundary tests are not blocked permanently. The bypass is auditable and reversible; production/CI should use `doctor --require-safety-authorization`, `run --require-safety-authorization`, or `make doctor-strict` to fail missing authorization.

`authorization.yaml` expiry is enforced. An optional `expires` date or RFC3339 timestamp must parse cleanly; expired bypass metadata remains visible in doctor JSON and TUI safety rows, but it no longer counts as current authorization and strict doctor gates block until the authorization is renewed or the boundary is restored.

Each production run now records a durable `workspace_safety` replay event before workspace bootstrap. Default runs keep disabled boundaries warning-only but auditable; `run --require-safety-authorization` uses the same current authorization check as strict doctor and blocks before provider, tool, or report execution when required safety bypass metadata is missing or expired. When a strict run proceeds, ordinary run worker-lease acquire and complete writes also recheck current authorization immediately before writing `workspace/runtime/worker-leases/<run-id>/`, so authorization removed or expired after startup still fails before those lease mutations.

Runtime-worker safety-bypass authorization is now enforced at twelve direct app side-effect gates: `ExecuteRuntimeWorkerQueueClaimDispatch`, worker-side HTTP receive/artifact ingress through `NewRuntimeWorkerTransportHTTPHandler` / `worker-transport-serve-http`, `CreateRuntimeWorkerTransportDaemonControlRequest` / `worker-transport-daemon-control` when writing pending daemon stop/restart control requests, `AcknowledgeRuntimeWorkerTransportDispatchRequest`, `ExecuteRuntimeWorkerTransportDispatchRequest`, `SubmitRuntimeWorkerQueueDispatchResult`, `ExecuteRuntimeWorkerDispatchRetryDispatch`, `UpdateWorkerLeaseHeartbeat`, `ReleaseWorkerLease`, `ExecuteWorkerLeaseReclaimDispatch`, `ExecuteWorkerLeaseResultReconciliationDispatch`, and `ExecuteRuntimeWorkerTransportDispatchDaemon` when `--enable-control` consumes pending daemon stop/restart controls. When `scope.target_policy` or `execution.isolation` is disabled without current matching `authorization.yaml` metadata, those gates fail before queue dispatch mutation or contact, accepted HTTP receive file-outbox artifact writes, pending daemon-control request creation, file-outbox request acknowledgement, worker request-command execution, worker queue dispatch result submission, retry-claim creation, active-lease heartbeat writes, active-lease release writes, stale-lease reclaim writes/execution audits, reconciliation release writes/execution audits, or pending daemon-control consumption, applied-status writes, and daemon audit control metadata. Worker-side HTTP receive still validates bearer token, worker id, and transport mode before the safety preflight, so missing or wrong bearer tokens return `401` responses without safety details; accepted receives write pending file-outbox artifacts only with current authorization under disabled boundaries. Daemon-control creation validates worker id/action before the safety preflight and writes pending metadata-only control artifacts only with current authorization under disabled boundaries. Higher-level loop, daemon, supervisor, orchestration, maintenance, and scheduler paths inherit this only when they delegate through those gates; the supervisor inherits daemon-control protection through child daemon runs and is not counted as another direct gate.

Result-callback HTTP is not counted separately; `NewRuntimeWorkerQueueDispatchResultHTTPHandler` / `worker-queue-dispatch-result-serve-http` accepts callbacks into `SubmitRuntimeWorkerQueueDispatchResult` and inherits that submission preflight. List/read, daemon-control list/read, and metadata-only planning/review paths keep their existing boundaries. Ordinary run lease acquire/complete writes are outside this runtime-worker direct gate list, but strict `ouro run --require-safety-authorization` now rechecks current authorization before those lease writes; default runs remain warning-only.

When `scope.target_policy: enforce` is active, command-runner argument checks cover standalone target literals plus embedded `key=value` and comma-list forms such as `--url=https://...`, `targets=a,b`, `--host=...`, and `--challenge=...`. `scope.target_policy: disabled` remains the explicit authorized off path for false-positive target-boundary cases.

URL-scoped `nuclei_jsonl` parser promotion treats `matched-at` as untrusted tool output: out-of-scope URLs collapse to the scoped URL target, and finding statements avoid `curl-command`, extracted result values, host/template URL noise, and request/response blobs. The durable fact metadata is limited to the scoped matched URL, target URL, template, severity, matcher/type, CWE/CVE, and execution identity.

URL-scoped `httpx_jsonl` parser promotion treats probe URLs and redirect/final URL fields as untrusted tool output: out-of-scope URLs collapse to the scoped URL target, and promoted URLs strip userinfo, query strings, and fragments. Durable surface facts are limited to scoped URL, target URL, status code, validated content type, content length, and execution identity. Titles, webserver/technology labels, headers, raw traffic, bodies, request/response blobs, screenshots, and redirect targets are not persisted in surface facts.

Host- or CIDR-scoped `nmap_xml` parser promotion treats XML hostnames/PTR data and scanner metadata as untrusted tool output. Host scope binds service facts to the scoped host target; CIDR scope promotes only XML IP addresses inside the scoped CIDR and skips out-of-scope or unverifiable hosts instead of collapsing them. Only `state="open"` ports become surface facts. Durable surface facts are limited to parser/tool/execution identity, scope kind/target, host/address metadata, protocol, port, open state, service name, tunnel, and service confidence. Scanner args/version/timestamps, raw XML, MAC/vendor, hostnames/PTR, OS match/class, uptime/distance, sequences, traceroute, runstats, extraports, port reasons, script output, and service product/version/CPE/fingerprint details are not persisted.

Domain-scoped `subfinder_jsonl` parser promotion accepts only explicit `kind: domain` scope and only promotes DNS names equal to that domain or child subdomains. URL scope is not converted into domain scope, even when `scope.target_policy: disabled` is configured. The parser accepts conservative string fields from simple JSONL (`host`, `subdomain`, `input`, or `domain`), normalizes lowercase ASCII LDH labels, trims one trailing dot, applies exact and `*.example.com`-style exclusions, and skips unsafe or out-of-scope records. Durable surface facts are limited to parser/tool/execution identity, domain, subdomain, confidence, and the compact statement. Raw lines, source metadata, IPs, resolvers, timestamps, errors, tokens, URLs, and unknown keys are not persisted.

CIDR-scoped `naabu_jsonl` parser promotion accepts only explicit `kind: cidr` scope and only promotes IP addresses inside that prefix that are not excluded. It accepts `ip` or IP-valued `host`, numeric or string `port` values from 1 through 65535, defaults protocol to `tcp`, allows `udp`, and formats IPv6 endpoints with brackets. Durable surface facts are limited to parser/tool/execution identity, IP, port, protocol, endpoint, target CIDR, confidence, and a compact open-port statement. DNS hostnames, timestamps, CDN flags, banners, errors, raw/request/response fields, and unknown keys are not persisted.

Domain-scoped `dnsx_jsonl` parser promotion accepts only explicit `kind: domain` scope and only promotes DNS observations for names equal to that domain or child subdomains. Managed execution writes a workspace-confined `dnsx-targets.txt` input file and runs `dnsx -j -silent -omit-raw -l <file>`; it deliberately does not use `dnsx -d`, because that flag is for brute forcing. Durable surface facts are limited to parser/tool/execution identity, domain, host, record type, value, optional address/CNAME field, confidence, and the compact statement. Resolver lists, raw responses, `all` records, CDN/ASN metadata, timestamps, errors, skipped names, and unknown JSON keys are not persisted.

URL-scoped `katana_jsonl` parser promotion accepts only explicit `kind: url` scope and only promotes route URLs under that scoped URL boundary. Managed execution runs `katana -u <url> -j -silent -or -ob -duc` to prefer JSONL and avoid raw request/response/body persistence. Durable surface facts are limited to parser/tool/execution identity, scoped route URL, target URL, method, status code, content length, depth, confidence, and the compact statement. Query strings, fragments, headers, raw traffic, request/response/body fields, forms, XHR request details, knowledgebase data, technologies, stored response paths, timestamps, errors, and unknown JSON keys are not persisted.

Domain-scoped `url_list_text` parser promotion accepts only explicit `kind: domain` scope for `gau/archive_discovery` and `waybackurls/archive_discovery`. Managed execution runs `gau <domain> --subs --providers wayback,otx,commoncrawl` or `waybackurls <domain>` and rejects excluded domain targets before argv generation. The parser promotes only HTTP(S) URLs whose host is the scoped domain or a child subdomain and skips excluded hosts/URLs. Durable surface facts are limited to parser/tool/execution identity, domain, sanitized URL, confidence, and a compact archive statement. Query strings, fragments, invalid lines, out-of-scope hosts, raw provider metadata, and unknown text are not persisted.

URL-scoped `ffuf_json` parser promotion accepts only explicit `kind: url` scope and only promotes non-excluded result URLs under that scoped URL boundary. Managed execution rejects excluded URL targets and generated wordlist candidate URLs before writing its workspace-confined `ffuf-wordlist.txt`, then runs `ffuf -w <file> -u <url>/FUZZ -json -s` without output files, debug logs, request-file inputs, replay proxies, or proxy flags. Durable surface facts are limited to parser/tool/execution identity, scoped URL, target URL, status code, content length, content words, content lines, validated content type, confidence, and the compact statement. Query strings, fragments, `input`, `position`, `redirectlocation`, `duration`, `resultfile`, `host`, `scraper`, raw request/response/body/header fields, file-output wrapper metadata, and unknown JSON keys are not persisted.

URL-scoped `dalfox_json` parser promotion accepts only explicit `kind: url` scope and promotes scoped XSS finding metadata from Dalfox JSON/NDJSON output. Managed execution rejects excluded URL targets before argv generation, then runs `dalfox url <url> --format json --silence --no-color --no-spinner` without found-action hooks, proxy/callback flags, remote payload/wordlist flags, config/raw-request inputs, debug output, HAR output, or request/response dump flags. Durable finding facts are limited to parser/tool/execution identity, scoped matched URL, target URL, finding type, injection type, PoC type, method, parameter, severity, CWE, confidence, and a compact statement. Query strings, fragments, payloads, evidence snippets, raw requests, raw responses, headers, bodies, messages, report wrapper data, and unknown JSON keys are not persisted.

Artifact/app static tooling is limited to explicit local artifact scope and workspace-managed payloads. Artifact target values resolve under `workspace/artifacts/`; traversal, symlinked artifact roots, symlink escape, outside-workspace paths, non-regular files, and outside artifact arguments whose paths contain `=` fail before execution. This filesystem boundary is not disabled by `scope.target_policy: disabled`. A challenge target does not authorize arbitrary local artifact scanning. Completed `mobsfscan_json` output is parsed into replay parser events and finding facts for the evidence graph; malformed JSON records `parse_failed` without failing the completed tool run or emitting facts. Reported file paths from the tool are treated as untrusted and persisted only as artifact-scoped identifiers with a separate `artifact_target` field.

Those settings are intentionally closeable. Return them to the stricter defaults when testing no longer needs the bypass, and use the strict doctor gate before production or CI-style runs.

Toolchain install dispatch and retry execution also use the strict safety-authorization preflight before running installer commands. Missing or expired authorization under disabled boundaries blocks installer execution instead of treating the bypass as a warning-only state.

Collaboration note focus now has the same closeable metadata boundary as saved sessions and collaborations. `replay-workbench-collaboration-note-select` writes `workspace/replay/workbench-collaboration-note-selection.json` with `status=current`; `replay-workbench-collaboration-note-selection` reads it; and `replay-workbench-collaboration-note-selection-clear` rewrites the same marker to `status=cleared`. `replay-workbench --enable-collaboration-note-selection-writes` is a separate explicit local browser gate for note focus. By default `POST /api/collaboration-note-selection` is rejected and the hosted page omits the note-selection form; when enabled, the page sets `window.OURO_REPLAY_COLLABORATION_NOTE_SELECTION_WRITES_ENABLED = true`, renders `#ouro-replay-collaboration-note-selection-form`, and accepts only structured `select` or `clear` JSON through the same workspace-confined note-selection marker writers. `replay-workbench --collaboration-note-selection-poll-interval-ms <ms>` is a separate explicit read-only refresh gate for note focus. Replay workbench session, collaboration, presence, note, note-selection, and report-selection write paths reject symlinked artifact directories, symlinked marker/artifact files, nested or outside artifact paths, and outside-sentinel overwrite attempts before writing. Accepted writes remain confined to `workspace/replay/workbench-sessions/`, `workspace/replay/workbench-collaborations/`, `workspace/replay/workbench-collaboration-presence/`, `workspace/replay/workbench-collaboration-notes/`, `workspace/replay/workbench-session-selection.json`, `workspace/replay/workbench-collaboration-selection.json`, `workspace/replay/workbench-collaboration-note-selection.json`, or `workspace/reports/report-projection-selection.json`. Browser writes remain default-off behind explicit `replay-workbench --enable-*-writes` flags, and enabling one write gate does not enable unrelated `POST` routes.

`replay-workbench --current-collaboration-note` restores the saved workbench session referenced by the current collaboration note selection. It requires `workspace/replay/workbench-collaboration-note-selection.json` to exist with `status=current` and a non-empty `note_path`, reads the selected note artifact, reads that note's collaboration artifact, then restores the collaboration's saved session defaults. It rejects `--session`, `--current-session`, and `--current-collaboration` conflicts, refuses cleared or missing note-selection markers, and remains read-only: it does not select or clear notes, edit notes or annotations, mutate replay events, start runs beyond normal replay loading, dispatch workers, or contact transports/targets.

`replay-workbench --enable-collaboration-stream` is the first live hosted collaboration stream. It exposes only `GET /api/collaboration-events` as `text/event-stream`, sends collaboration artifact, selection, note-selection, presence, and note snapshots, and broadcasts refreshed snapshots after the existing gated selection/presence/note/note-selection browser writes. `replay-workbench --collaboration-stream-refresh-interval-ms <ms>` is a separate server-side read-only refresh gate for active SSE subscribers: default `0` disables workspace refreshes, while a positive interval reloads only workspace-confined collaboration artifacts, presence artifacts, note artifacts, and the current/cleared selection markers before writing the next SSE snapshot. The stream and refresh path are default-off/read-only and do not create POST routes, write workspace files, start runs, dispatch workers, contact transports or targets, or mutate replay events.

Runtime worker bounded commands fail before mutation when their explicit bounds are invalid. `worker-transport-run-loop`, `worker-transport-run-daemon`, `worker-transport-run-supervisor`, `worker-lifecycle-maintenance-supervisor`, and `worker-orchestration-supervisor` reject non-positive run/request/idle/poll limits instead of silently defaulting and writing audit artifacts.

Replay and HTTP receiver bounds now fail closed on invalid negative limits while preserving `0` as the explicit unbounded/local-test mode. `replay-workbench --max-requests`, `runtime worker-transport-serve-http --max-requests`, and `runtime worker-queue-dispatch-result-serve-http --max-results` reject negative values before replay loading, token lookup, listener creation, request handling, artifact writes, worker dispatch, endpoint contact, or tool execution.

Worker queue ownership and orchestration bounds now fail before mutation on invalid operator input. `runtime execute-worker-placement-plan --lease-seconds`, `runtime worker-queue-claim --lease-seconds`, `runtime worker-orchestrate --lease-seconds`, `runtime worker-orchestration-supervisor --lease-seconds`, and `runtime execute-worker-dispatch-retry-dispatch --lease-seconds` require positive values; placement-dispatch and orchestration `--max-candidates` reject negative values while preserving `0` as "all"; and `worker-queue-claim --run-timeout-ms` rejects negative values while preserving `0` as "no per-request timeout".

Runtime worker transport token lookup is now scoped to explicit execution and real `http-json` transport. `runtime execute-worker-queue-claim` and `runtime execute-worker-placement-dispatch-plan` report the missing `--execute` gate before reading `--transport-token-env`, and placement-dispatch execution reads the persisted plan transport before token lookup so `metadata-only` and `file-outbox` plans remain executable even if a missing token env name is supplied. `runtime worker-orchestrate` / `runtime worker-orchestration-supervisor` dry-runs do not require a bearer token even when the planned transport is `http-json`. Metadata-only and file-outbox paths remain reviewable without secret/env access, while actual `http-json` execution still reads the token only from the named environment variable and does not persist it.

Worker lifecycle policy artifacts are metadata-only strategy input for explicit policy-run execution. `runtime worker-lifecycle-policy <workspace>` previews a dry-run metadata-only policy from the current lifecycle audit summary, and `--write` persists metadata-only JSON under `workspace/runtime/worker-lifecycle-policies/` with stale lease thresholds, worker staleness threshold, poll interval metadata, max supervisor runs, planned transport, lifecycle-maintenance inclusion, lifecycle-retry policy, a separate default-off lifecycle retry handoff policy, and default-off lifecycle lease-recovery policy. `--dispatch-lifecycle-retry-claims` is accepted only with `--include-lifecycle-maintenance` and `--execute-lifecycle-retry-dispatches`; its separate `--lifecycle-retry-transport` accepts only `metadata-only` or `file-outbox`, rejects `http-json`, and records default-off policy intent consumed only by explicit policy-run/scheduler-run paths. `--execute-lifecycle-lease-recovery` is accepted only with `--include-lifecycle-maintenance`; it records default-off policy intent consumed only by explicit policy-run/scheduler-run paths and does not mutate leases by itself. `runtime worker-lifecycle-policy-select <workspace> <artifact>` writes the closeable current marker at `workspace/runtime/worker-lifecycle-policy-selection.json` with `status=current`, making the artifact the current strategy input; `runtime worker-lifecycle-policy-selection <workspace>` reads it; and `runtime worker-lifecycle-policy-selection-clear <workspace>` rewrites the same marker to `status=cleared`, explicitly disabling current strategy/focus without deleting audit context. When surfaced in workspace-bound Agent Runtime, double-confirm `x` selects noncurrent policy artifacts or clears a current selection row. Policy artifacts and the marker are metadata-only scheduler inputs: poll interval is stored policy metadata only, default Ouroboros starts no autonomous lifecycle scheduler, and these paths reject invalid bounds/transports plus lifecycle retry, lifecycle retry handoff, or lease recovery without the required lifecycle maintenance/retry gates before writes while creating no supervisor, maintenance, queue-claim, transport, endpoint, target, execution artifact, lease, result, or tool side effects. `runtime worker-lifecycle-policies <workspace> [artifact]` lists or inspects persisted policies, and workspace-bound Agent Runtime renders policy rows as Inspector metadata.

`CreateWorkerLifecyclePolicyRun` / `ouro runtime worker-lifecycle-policy-run <workspace> [--execute]` is the explicit policy runner for the current worker lifecycle strategy, and it consumes only `workspace/runtime/worker-lifecycle-policy-selection.json` when that marker has `status=current`. A missing or cleared marker fails closed. The default run writes a metadata-only policy-run audit artifact under `workspace/runtime/worker-lifecycle-policy-runs/` and creates no supervisor, maintenance, queue, transport, request, result, lease, or tool side effects. `--execute` is still explicit and bounded: it creates at most one maintenance supervisor using the selected policy's `MaxSupervisorRuns`, `StaleAfterSeconds`, `ExecuteLifecycleRetries`, `DispatchLifecycleRetryClaims`, `LifecycleRetryTransportMode`, and `ExecuteLeaseRecovery`. If the selected policy disables lifecycle maintenance, it writes a completed/skipped policy-run audit artifact with skip reason `lifecycle-maintenance-disabled` and no supervisor. Lifecycle retry handoff remains subordinate to the selected policy's explicit lifecycle retry execution gate: without the selected handoff flag it stops at metadata-only retry queue claims; with the selected handoff flag it may only create metadata-only queue-dispatch audits or pending file-outbox requests through the existing queue-dispatch gate. It is not a resident scheduler: it has no sleep, ticker, background goroutine, repeated invocation, endpoint contact, target contact, transport contact, acknowledgement, stored tool-plan command execution, result submission, daemon control, or tool execution beyond the existing explicit child gates.

Worker lifecycle policy scheduler runs are now implemented as a bounded, non-resident launcher above policy-run. `ouro runtime worker-lifecycle-policy-scheduler-run <workspace> [--execute --max-runs N]` consumes only the current `runtime/worker-lifecycle-policy-selection.json` marker and revalidates the selected policy artifact before any write. The default scheduler run writes one metadata-only dry-run audit under `workspace/runtime/worker-lifecycle-policy-scheduler-runs/` and creates no child policy-runs or supervisor artifacts. `--execute` requires a positive `--max-runs`, creates at most that many policy-run children through the existing policy-run gate, and exits without sleep, ticker, or background scheduling. Lease recovery and lifecycle retry handoff automation remain default-off: scheduler execution may release/reclaim leases only when the selected policy's explicit recovery gate is enabled, and may hand off retry claims only when the selected policy enables lifecycle maintenance, lifecycle retry execution, and lifecycle retry handoff with `metadata-only` or `file-outbox` transport. A cleared policy marker or `poll_interval_ms=0` is the close/off path and creates no recovery or retry-handoff children. Missing, cleared, empty, invalid, or tampered selections, invalid selected policy bounds, unsupported transports, negative poll intervals, and negative dry-run `--max-runs` fail closed before writes. `ouro runtime worker-lifecycle-policy-scheduler-runs <workspace> [artifact]` lists or inspects scheduler-run audits. Workspace-bound Agent Runtime renders scheduler-run rows read-only, where `d` opens details only and `x` / `r` do not execute or request anything. The scheduler-run safety invariant is no endpoint, target, or transport contact; no acknowledgement; no stored tool command execution; and no result submission. The only enabled retry handoff side effect is an explicit metadata-only queue-dispatch audit or pending file-outbox request.

Worker dispatch retry scheduler runs are now implemented as a bounded, non-resident launcher over the retry plan, retry-dispatch, and retry-dispatch execution gates. `ouro runtime worker-dispatch-retry-scheduler-run <workspace> [--execute --max-runs N]` writes scheduler-run audits under `workspace/runtime/worker-dispatch-retry-scheduler-runs/`, and `ouro runtime worker-dispatch-retry-scheduler-runs <workspace> [artifact]` lists or inspects them. The default dry-run writes only that scheduler audit and creates no retry plans, retry dispatches, retry-dispatch executions, queue claims, queue dispatches, outbox requests, HTTP calls, acknowledgements, results, lease mutations, daemon/control artifacts, or tool executions. Execution is closed unless both `--execute` and a positive `--max-runs` are supplied; it creates at most `N` bounded retry plan, dispatch, and execution steps, dedupes already-retried source results so the same failed result is not claimed repeatedly, and default execution creates metadata-only retry queue claims only. Optional retry claim handoff is a separate default-off gate enabled only with `--dispatch-retry-claims --retry-transport metadata-only|file-outbox`; `http-json` is rejected, so handoff may create only metadata-only queue-dispatch audits or pending file-outbox requests. Omitted `--execute`, omitted handoff, and the `--max-runs` bound are the close/off paths, and the slice has no endpoint or target contact, stored command execution, result submission, acknowledgement, daemon control, lease mutation, or tool execution.

Worker lifecycle audit reports now also aggregate lifecycle policy state as read-only reporting metadata. `runtime worker-lifecycle-audit` reads existing lifecycle policy artifacts, the current/cleared policy-selection marker, policy-run artifacts, and scheduler-run artifacts as audit items and counts only. It also mirrors persisted action-plan annotation and current/cleared action-plan selection marker state without writing the action-plan JSON or marker. The audit is reporting-only: it does not create policy-runs, scheduler-runs, supervisors, queue claims, outbox requests, endpoint/transport/target contact, acknowledgements, result submissions, lease mutations, or tool execution.

Workspace-bound TUI RuntimeActions fail closed before requester callbacks. Pressing `r` is requestable only for explicit metadata request actions such as `install` remediation rows; read-only rows such as compile-preview review comparisons, cleared selection markers, replay collaboration presence, workspace safety gates, worker lifecycle audit items, policy-run artifacts, and scheduler-run artifacts return `request status: unsupported` plus `request error: runtime action is read-only` without creating a command or invoking the workspace requester. Current closeable metadata actions that are not request requests return `runtime action does not support requests`, while their double-confirm `x` paths remain separate.

Worker lifecycle maintenance now has separate explicit retry-dispatch, retry-handoff, and lease-recovery execution gates. Default `runtime worker-lifecycle-maintenance --execute` still skips ack, run-once, daemon-control, retry-dispatch execution, and lease recovery execution recommendations as `requires-explicit-operator-gate`. Only `--execute --execute-lease-recovery` may invoke the existing lease reclaim / lease-result reconciliation execution gates, and it must not dispatch claims, write outbox requests, contact endpoints or targets, acknowledge requests, run commands, submit results, apply daemon controls, or execute tools. Only `--execute --execute-retry-dispatches` invokes the retry-dispatch execution gate, creating retry-dispatch execution audit artifacts and metadata-only retry queue claims; without the handoff flag, retry execution stops there. The extra `--dispatch-lifecycle-retry-claims --lifecycle-retry-transport metadata-only|file-outbox` handoff is subordinate to that retry gate; it rejects `http-json`, may create only metadata-only queue-dispatch audits or pending file-outbox requests, and still does not contact endpoints or targets, acknowledge requests, run stored tool-plan commands, submit results, apply daemon controls, release/reclaim leases, or execute tools. Supplying handoff without `--execute` or `--execute-retry-dispatches` fails before writing maintenance artifacts.

The bounded maintenance supervisor exposes the same non-default gates. Default `runtime worker-lifecycle-maintenance-supervisor --execute --max-runs <n>` still repeats metadata-only maintenance/audit passes and leaves retry-dispatch, retry-handoff, and lease-recovery execution skipped. Adding `--execute-lease-recovery` passes the explicit recovery gate into each bounded maintenance pass and aggregates reclaim/reconciliation execution and result counts. Adding `--execute-retry-dispatches` passes the explicit retry gate into each pass and aggregates retry-dispatch execution/claim counts. Adding `--dispatch-lifecycle-retry-claims --lifecycle-retry-transport metadata-only|file-outbox` further hands those newly created retry claims to the existing queue-dispatch gate and aggregates dispatched/request counts. Handoff is rejected without `--execute` and `--execute-retry-dispatches`, rejects `http-json`, and preserves the no-endpoint/target, no-ack, no-command, no-result-submission, no-daemon-control, no-lease-mutation, and no-tool-execution boundary.

Top-level worker orchestration can now pass that same lifecycle retry gate only when the lifecycle attachment is explicitly enabled. Default `runtime worker-orchestrate --execute --include-lifecycle-maintenance` still creates metadata-only lifecycle maintenance/audit artifacts and skips retry-dispatch execution; adding `--execute-lifecycle-retry-dispatches` requires both `--execute` and `--include-lifecycle-maintenance`, then creates retry-dispatch execution audits plus metadata-only retry queue claims through the existing maintenance path. The separate `--dispatch-lifecycle-retry-claims --lifecycle-retry-transport metadata-only|file-outbox` flag can then hand those claims to the existing queue-dispatch gate; it rejects `http-json` and can create only metadata-only dispatch audits or pending file-outbox requests. It still does not contact endpoints or targets, acknowledge requests, run stored tool-plan commands, submit results, apply daemon controls, release/reclaim leases, or execute tools.

The bounded worker orchestration supervisor can pass that same lifecycle retry gate into each child orchestration only through its own explicit flag. Default `runtime worker-orchestration-supervisor --execute --max-runs <n> --include-lifecycle-maintenance` still creates bounded metadata-only child lifecycle maintenance/audit artifacts and skips retry-dispatch execution. Adding `--execute-lifecycle-retry-dispatches` requires both `--execute` and `--include-lifecycle-maintenance`, aggregates `retry_dispatch_executions_created` and `retry_dispatch_claims_created`, and links retry-dispatch execution audit paths. Adding `--dispatch-lifecycle-retry-claims --lifecycle-retry-transport metadata-only|file-outbox` further aggregates dispatched/request counts through the existing queue-dispatch gate. Handoff rejects `http-json` and preserves the same no-endpoint, no-ack, no-command, no-result, no-daemon-control, and no-lease-mutation boundary; pending file-outbox requests still require the existing ack/run/result-return gates.
