## Risks / Decisions
- Replay requires both workspace path and run id so it can locate the correct SQLite event log.
- Replay calls `DoctorWorkspace` first, so it rejects broken workspaces before attempting to read event data.
- Toolchain inspection calls `DoctorWorkspace` first, so manifest inspection and health checks reject invalid workspaces consistently.
- `--tui` intentionally prints a snapshot first, giving automated tests and logs access to the TUI-first state before wiring a long-running interactive program.
- `--interactive` uses an injectable runner in the CLI package so tests can verify the selected `tui.Model` while the production path still launches Bubble Tea with alt-screen enabled.
- Run streaming observers are invoked only after SQLite append succeeds, so live consumers see durable event IDs and timestamps rather than speculative in-memory events.
- Interactive run sends replay snapshots to the TUI session only after durable appends; if the run errors, the CLI asks the session to quit so the error can surface.
- Interactive cancel uses a runtime control requester instead of making `q` or `ctrl+c` implicitly cancel a run. This keeps quitting the UI separate from an audited operator request to cancel the run context.
- Interactive pause/resume is intentionally admission-scoped. It prevents queued workers from starting and surfaces `run_paused` as a durable wait reason, but it does not pause or signal a child process that has already started.
- Replay cursor stepping rebuilds snapshots from persisted events up to the selected cursor, keeping replay state derivation deterministic and aligned with the event log.
- Replay app results expose cursor-ready TUI models while keeping textual replay summaries unchanged.
- Timeline rows intentionally derive current event metadata from the same persisted event cursor used to rebuild the replay snapshot.
- Tool worker rows derive from replayed `worker_status` queued/waiting/started events and final `execution_status` events keyed by `execution_id`; final command result events remain separate from worker lifecycle events to avoid confusing result parsers.
- Final tool execution result events now stream as individual workers complete, so live snapshots can show completed/failed workers while other queued or active workers are still running.
- Pack execution policies are scheduler admission controls, not safety bypasses. `mode: disabled` skips a named pack for the current workspace policy while preserving target-boundary and isolation settings for any pack that is still admitted.
- Scheduler admission events deliberately use `admission_action` and `admission_capability` instead of final execution fields, so replay/TUI can show policy decisions without polluting worker lifecycle or final result projections.
- Pack `max_concurrency`, worker-pool `max_concurrency`, CPU/memory leases, runtime worker registration artifacts, placement-plan artifacts, placement-claim execution artifacts, placement-dispatch plan artifacts, placement-dispatch execution and batch artifacts, worker queue claim artifacts, runtime worker queue dispatch/result audits, file-outbox request artifacts, runtime worker lease artifacts and active-lease heartbeat/release controls, and `execution.worker_pools` are local in-process scheduler controls or metadata views, not distributed worker placement or container/cgroup enforcement. The local scheduler now acquires global, worker-pool, pack, and resource capacity atomically and records worker ids for audit; worker registrations persist local/remote identity/status/capability metadata for operator visibility and can be refreshed by external heartbeat updates; placement plans stay dry-run metadata until an explicit placement-claim gate revalidates one ready candidate and creates only a metadata-only queue claim; placement-dispatch plans revalidate those placement-derived claims as dry-run dispatch candidates without mutating queue state; placement-dispatch execution then revalidates one candidate or, with the batch gate, each ready candidate, and delegates to the queue-dispatch gate while preserving default metadata-only transport unless the plan selected `file-outbox` or `http-json`; top-level worker orchestration now writes `runtime/worker-orchestrations` audit artifacts, stays dry-run/metadata-only by default without child artifacts, and with `--execute` composes placement-plan creation, bounded placement claims, placement-dispatch planning, and the existing batch gate without adding a resident scheduler or TUI execution shortcut; `--include-lifecycle-maintenance` is an additional non-default execution option that creates only metadata-only lifecycle maintenance and lifecycle audit artifacts after that composition and links them from the orchestration artifact; queue claims persist metadata-only ownership after stale/offline/capability checks, can carry structured tool-plan payloads, can be explicitly canceled/released only while still `claimed`, can be explicitly marked expired only after `expires_at` elapses, and can be explicitly renewed before expiry; queue dispatch execution explicitly consumes valid claims and can write file-outbox requests without contacting remote endpoints, or explicitly POST the same request JSON to an `http-json` worker endpoint after the operator selects that transport, with optional bearer auth sourced from env and represented only as an audit marker; worker-side HTTP receive persists authorized requests back into the same file-outbox boundary and rejects bad bearer tokens before artifact writes; file-outbox requests can be listed, inspected, acknowledged through CLI or TUI double-confirm, explicitly executed once, processed in a bounded loop, polled by a resident daemon, or composed by a bounded daemon supervisor through either an operator-supplied command or each request's stored `tool_plan.run_command`, with request-carried tool-plan env context; daemon run and daemon supervisor audit artifacts persist bounded worker-side state for CLI/TUI review; daemon stop/restart controls are metadata-only requests that are ignored unless a daemon or supervisor is launched with `--enable-control`; supervised restarts stop at `restart-limit` when `--max-runs` is exhausted; TUI `x` on a daemon run artifact writes only a pending stop control request after double confirmation, and TUI `R` writes only a pending restart control request after double confirmation; neither shortcut stops or restarts a daemon directly; result return and HTTP result callbacks close dispatches, claims, and linked outbox requests through audit artifacts; lease artifacts persist active/completed/failed/stale/reclaimed-visible worker state, acquisition is no-overwrite atomic for a single run/execution id, active leases can be explicitly heartbeat-refreshed or released without reclaim/dispatch side effects, lease/result reconciliation remains read-only and only recommends a later release for returned-result/active-lease mismatches, persisted reconciliation reviews stay dry-run/metadata-only, a separate explicit release execution gate revalidates those reviews and only releases still-active matching leases, TUI `x` can invoke that same gate only after double confirmation, and stale active leases can be planned, persisted, and explicitly reclaimed through an audit gate. Lifecycle policy artifacts keep poll interval as metadata only; the current/cleared policy-selection marker is the only policy-run input; policy-run audits are metadata-only by default; `--execute` can create at most one maintenance supervisor or a `lifecycle-maintenance-disabled` skipped audit; selected lifecycle retry handoff is default-off, rejects `http-json`, and can only create metadata-only queue-dispatch audits or pending file-outbox requests through existing child gates; and TUI policy-run rows are read-only with no execution shortcut. None of those policy paths start a sleep/ticker loop, background goroutine, or repeated invocation, or contact endpoints/targets. Full distributed placement remains future work.
- Pack container overrides are shallow first-pass inheritance: strings, slices, pointers, and positive numeric fields override global container values, while `read_only_rootfs` only tightens to `true` for now. Relaxing inherited booleans needs a later normalized policy representation.
- Install-plan rows remain metadata-only remediation hints; neither CLI nor TUI executes installer commands automatically.
- Install dispatch artifacts are dry-run snapshots of approved requests. They are designed as an audit and review boundary before any future execution dispatcher, not as an execution trigger.
- Dispatch artifact inspection accepts only basenames or paths confined to `workspace/toolchain/install-dispatches/`, matching the path-safety rule already used for install-request status updates.
- TUI dispatch execution intentionally requires selecting a dry-run dispatch artifact and pressing `x` twice; the first press only arms confirmation, and the second press reuses the same app execution gate as `execute-install-dispatch --execute`.
- Execution artifact rows appended after TUI-triggered execution are generated by the app executor from the just-written audit artifact, avoiding a second process execution during UI refresh.
- Failed TUI-triggered execution still writes and refreshes from the execution audit artifact created by `ExecuteToolchainInstallDispatch`; the UI preserves partial output/error metadata instead of collapsing the result to a generic failure.
- Execution audit artifact inspection accepts only basenames or paths confined to `workspace/toolchain/install-executions/`; listing, CLI inspection, and TUI rendering are read-only views over JSON artifacts.
- Execution audit artifact/result detail inspection in the TUI is intentionally read-only and uses the existing Node Inspector path rather than a new execution shortcut.
- Runtime Tab selection, activation, and detail inspection are UI state over replay-derived rows. They highlight and acknowledge the active row, expose structured command details for later dispatch, clear stale feedback when rows/selection change, and do not mutate replay data or execute remediation.
- `toolchain install-plan` intentionally shares the same metadata-only rule as the TUI remediation path: it surfaces command arrays for inspection or copying, but does not run installer commands.
- Exec health probes are direct command arrays rather than shell strings, so workspace manifests can check binaries without adding shell parsing semantics.
- Command runner manifests also use direct command arrays rather than shell strings. Process mode uses an attempt-scoped host working directory; container mode maps the equivalent workspace path under `/workspace`.
- Container isolation invokes a configurable engine with direct arguments. It intentionally does not resolve the inner `run_command` binary on the host; the selected container image owns tool availability.
- Container mode now emits first-pass sandbox args, including resource limits, network profile, read-only rootfs, seccomp/AppArmor, and tmpfs, and `doctor` checks engine/image availability before runs. Container-image dependency health commands can verify local image digests. Pack-level container inheritance can override selected image/network/resource fields. Container mode still mounts the workspace read-write at `/workspace` and does not yet configure user namespace remapping.
- Dependency checking currently detects binary readiness through direct commands, requires declared SHA-256 provenance for required container-image dependencies, verifies local image digests through health-command inspect output, can fetch update metadata from declared local/remote metadata sources, and uses manifest `depends_on` to order unresolved install-plan rows plus approved dispatch candidates. Installer execution is handled only by explicit approved dispatch/retry gates or the top-level `install-orchestrate --execute` audit flow, and retry execution remains separate.
- Scope target templates are expanded only from workspace `scope.yaml`; target templates without a matching scoped target fail closed before command execution.
- Command worker environments intentionally avoid inheriting host variables such as `HOME`; commands receive explicit `OURO_*` context plus `PATH` for binary resolution.
- `run_timeout_ms` is optional and measured in milliseconds; `0` or omission means the command is bounded only by the parent run context.
- Command timeout is treated as a failed tool execution, not a successful empty transcript. The failed event is replayable and report projection is skipped.
- Replay report paths are derived only from `report_ready` events. A failed run without report projection is shown as `not-generated`, even though its failed tool events remain replayable.
- Command-bound tool execution is for scoped target work. Tool/version probes without target scope belong in `healthcheck: exec`, not the `tool-execution` stage.
- `scope.exclusions` now supports exact trimmed matching, URL subtree/trailing-slash/default-port normalization, CIDR/IP containment, and explicit `*` wildcard exclusions for URL/CIDR/challenge target values. Richer URL normalization remains future work.
- `scope.target_policy: disabled` is an explicit workspace-level escape hatch for authorized false-positive scope boundaries. It bypasses command-runner target and exclusion checks, but command templates still require concrete `{{target}}` values.
- Web/API command argument policy scans standalone, embedded `key=value`, and comma-list `http://` / `https://` URL literals. It enforces scheme, normalized host/default-port, and path boundary against the scoped URL target; richer URL normalization remains future work.
- Infra/Internal command argument policy scans standalone, embedded `key=value`, and comma-list IP/CIDR literals. It enforces address/prefix containment inside the scoped CIDR target; range notation remains future work.
- CTF/Lab command argument policy scans explicit `challenge:<id>` and `ctf://<id>` literals, including embedded `--challenge=...` and `target=...` forms. Bare words are intentionally not interpreted as challenge IDs to avoid false positives.
- `execution.isolation: process` is the current default and means constrained child process. `execution.isolation: container` is the first container-engine boundary with configurable sandbox args. `execution.isolation: disabled` is intentionally less isolated and should be reserved for authorized compatibility cases.
- `doctor` warnings are intentionally non-blocking for explicit bypasses; they make authorized exceptions visible without preventing false-positive boundary testing.
